# Архитектура компилятора, C-интерфейс и этапы развития lac

Дата проверки источников: 2026-10-01. Прочитаны AGENTS.md, MEMORY.md, docs/language.md, docs/draft-01.md и docs/roadmap.md. Это исследовательские предложения: утверждённая спецификация не изменена, коммиты не создавались.

## Как организовать первый компилятор, сохранив генерацию C?

### Takeaway

Генерация C подходит утверждённому первому драфту Linux/Windows. Предлагается сохранить собственную семантику lac в типизированном внутреннем представлении и только после проверок понижать её в C, не превращая фронтенд в набор текстовых подстановок.

### Cited Findings

- Американская научная работа: Chris Lattner, Vikram Adve, University of Illinois at Urbana-Champaign, **LLVM: A Compilation Framework for Lifelong Program Analysis & Transformation**, CGO 2004, Palo Alto. Официальная страница публикации подтверждает авторов, место и дату; статья предлагает общее низкоуровневое представление SSA с независимой от исходного языка системой типов. Применимость: аргумент за разделение фронтенда и бэкенда, но не требование внедрять LLVM или SSA в lac 0.1. [Официальная публикация LLVM](https://llvm.org/pubs/2004-01-30-CGO-LLVM.html).
- Европейская научная работа: Xavier Leroy, INRIA Paris-Rocquencourt, Франция, **Formal verification of a realistic compiler**, Communications of the ACM 52(7), 107–115, 2009. Авторская PDF и официальный список публикаций подтверждают происхождение и библиографию. Описаны несколько промежуточных языков и сохранение наблюдаемого поведения; статья подчёркивает сложность даже не оптимизирующих преобразований. Применимость: определить семантику вычислений и контракт каждого прохода. Генерация C или использование CompCert не делает перевод lac автоматически доказанно корректным. [Авторская статья](https://xavierleroy.org/publi/compcert-CACM.pdf), [библиография проекта](https://compcert.org/publi.html).
- GCC поддерживает C11/C17/C23, причём C17 — исправления C11; текущая документация описывает GNU C23 как режим по умолчанию. Поэтому режим нельзя оставлять зависимым от версии установленного GCC. [GCC: Standards](https://gcc.gnu.org/onlinedocs/gcc/Standards.html).
- MSVC поддерживает C11/C17 с Visual Studio 2019 16.8 и соответствующим SDK/UCRT; для C17 документированы `/std:c17` и сборка именно как C. [Microsoft: C11/C17](https://learn.microsoft.com/en-us/cpp/overview/install-c17-support?view=msvc-170).
- Директива `#line` меняет сведения о файле и строке для диагностик, но не является полноценной картой каждой колонки и каждого синтетического выражения. [GCC: Line Control](https://gcc.gnu.org/onlinedocs/cpp/Line-Control.html).

### Inferences

Все следующие пункты — проектные рекомендации на основе исследований, а не принятые решения пользователя.

**Предлагаемая цепочка:**

```text
исходник → токены с позициями → AST → разрешение имён и типов
         → типизированный HIR → нормализованное IR → C
         → C-компилятор и линкер → исполняемый файл
```

- AST хранит исходные формы, позиции и значения литералов. Типизированный HIR связывает каждое имя с определением, разрешает конструкторы, размещение и перегрузки, превращает `.` в идентификатор конкретного аргумента. Небольшое IR делает явными порядок вычислений, временные значения, переходы, выделение памяти и вызовы runtime. Эти два внутренних слоя можно сначала реализовать компактно, без самостоятельного фреймворка оптимизаций.
- Не переносить неопределённость C в lac случайно. Если выбирается порядок аргументов слева направо, `f(g(),h())` должно понижаться через отдельные временные значения. Аналогично явно понижать короткое замыкание, выражение блока, возврат значения и проверки границ. Цель — один результат при `-O0` и `-O2`, на обеих платформах.
- Предложение: генерировать переносимое подмножество **C17**, не полагаясь на VLA, GNU nested functions или statement expressions. C11 даст почти тот же набор нужных средств; C23 не нужен для начального ядра. Нужен тестовый профиль конкретных GCC/Clang/MSVC, а не обещание «любой компилятор C».
- Статическая функция превращается в C-функцию. Замыкание — структура окружения плюс функция с аргументом окружения. Состояние sequence — отдельная структура и операция next; это не обязательно coroutine C-компилятора. Единый runtime хранить как версионированные `lac_runtime.h/.c`, с небольшими платформенными адаптерами. Встраивание runtime в конечную сборку не означает встраивание внешних утилит.
- Сначала выдавать ошибки lac до C-генерации. Сохранять `file/span` в AST/HIR/IR, добавлять `#line`, хранить генерируемый C по опции отладки; ошибки C toolchain разделять на «импорт/линковка», «неподдерживаемый toolchain» и «ошибка генератора». Не показывать ошибку генерируемого C как якобы ошибку пользователя lac без проверки происхождения.
- Язык реализации не выбран. Rust — практичный кандидат для enum AST/HIR, проверки памяти реализации и запуска процессов через отдельные аргументы; интеграция с Clang C API добавляет FFI и упаковку библиотек. C++ — кандидат при прямом использовании Clang AST/LibTooling и навыках автора, но сложнее поддерживать собственную память реализации. Выбирать после маленького прототипа импорта и генерации C. Язык реализации не определяет безопасность исполняемого lac.

### Gaps

- Нет утверждённой грамматики неоднозначных строк, разделителей объявлений и точного порядка вычислений. Это блокирует корректный парсер сильнее выбора бэкенда.
- Не утверждены язык реализации, архитектуры процессора, минимальные версии ОС, конкретный C toolchain, политика переполнения и алгоритм GC. Linux/Windows не означают автоматически кросс-компиляцию.
- Обещание «вывод программы lazy в строке» требует отдельного контракта входа: когда возникает материализация, что делает `.size`, как работает повторное чтение. В драфте без внешних команд возможный источник — стандартный ввод, но это только предложение.

## Что требуется для корректного `import header.h` и границы lac/C?

### Takeaway

`#include` в сгенерированном C недостаточно для строгой проверки lac: фронтенд должен знать сигнатуры до генерации. Самая практичная предлагаемая реализация — читать C translation unit через Clang, ограничить поддерживаемые декларации первого драфта и явно отделить C-указатели от управляемых ссылок lac.

### Cited Findings

- libclang предоставляет AST, типы деклараций и позиции исходника через относительно стабильный C API, однако официально не обещает доступ ко всей информации C++ AST. [Clang: Libclang tutorial](https://clang.llvm.org/docs/LibClang.html).
- `-D`, `-U`, пути include и зависимые заголовки участвуют в препроцессировании; `-M`/`-MD` и родственные параметры GCC позволяют получить зависимости. Следовательно, заголовок нельзя понимать изолированно от конфигурации сборки. [GCC: Preprocessor Options](https://gcc.gnu.org/onlinedocs/gcc/Preprocessor-Options.html).
- В MSVC `int` и `long` имеют 32 бита даже в 64-битной конфигурации, `long long` — 64; `wchar_t` в приведённом профиле 16-битный. Документация прямо предупреждает, что переносимый код не должен выводить размер `int` только из его имени. [Microsoft: Data Type Ranges](https://learn.microsoft.com/en-us/cpp/cpp/data-type-ranges?view=msvc-170).

### Inferences

- **Фиксированные lac-типы и C ABI — отдельные сущности.** Предложение для C-эмиссии: `i→int64_t`, `u→uint64_t`, `i32→int32_t`, `u32→uint32_t`, `f→float`, `d→double`, `c→uint16_t` после подтверждения кодовой единицы UTF-16, `b→bool`/`_Bool`. Импортированный C `int` остаётся C `int`, а не автоматически lac `i`. Извлекать layout/types для того же target, ABI, defines и include paths, которые использует сборка.
- Нужны параметры импорта: имя/путь header, системный или локальный поиск, target, defines, include directories. Нужна отдельная конфигурация линковки: библиотека, пути поиска и дополнительные объектные файлы. Header описывает API, но сам по себе не предоставляет реализацию внешней функции.
- Предложенный минимальный FFI: функции с фиксированной сигнатурой, арифметические типы, простые C-структуры/opaque handles, ограниченные pointers. Макросы-функции, varargs, callback-замыкания, bitfields, unions и сложные указатели сначала диагностировать как неподдерживаемые, а не молча угадывать. `puts` лучше для первого smoke test, чем `printf`: у последнего есть varargs и контракт форматной строки. Произвольный header можно импортировать, но это не значит, что каждый его construct поддерживается сразу.
- Два честных маршрута реализации FFI. **Сразу libclang:** надёжнее понимать реальную конфигурацию стандартных и системных headers, но добавляет зависимость и target setup уже в MVP. **Ограниченный интерфейс с декларациями:** пользователь/стандартный binding описывает поддерживаемую сигнатуру в lac либо отдельном manifest, generated C включает header и C-компилятор проверяет совместимость; это меньший прототип, но изменение требований нуждается в согласовании, поскольку простой `import header.h` тогда не даёт автоматического доступа к произвольным функциям. Самописный parser деклараций допустим для специально ограниченных собственных headers; не рекламировать его как parser всей C стандартной библиотеки. Ручной binding `puts` полезен как промежуточная веха, но не закрывает утверждённое требование автоматического импорта.
- Неполная информация об ownership не восстанавливается автоматически по `T*`. Для pointer-параметра нужно знать: заимствует ли C память до возврата, сохраняет ли адрес, модифицирует ли буфер, кто освобождает результат и каким destructor. GC должен учитывать FFI-пиннинг/корни; unmanaged handle не должен уничтожаться как обычный объект lac.
- UTF-16 `s` не передавать как `char*` путём cast. Предложение: явные адаптеры в UTF-8/другую нужную кодировку и NUL-terminated буфер либо пару pointer+length. Указать политику для встроенного NUL и некорректных UTF-16 последовательностей. Не использовать `wchar_t` как универсальное переносимое представление lac `c`.
- C допускает nullable возвращаемые pointers независимо от запрета null в lac. Нужен boundary adapter: проверка результата и ошибка/вариант отсутствия, ещё не утверждённый по синтаксису. «Без null» в lac нельзя гарантировать одной декларацией импортированного типа.

### Gaps

- Пользователь не определил синтаксис C-типов, foreign pointers, link flags, ownership contracts, varargs и callbacks. Первому драфту нужна явно опубликованная таблица поддерживаемого FFI.
- Проверка не охватывает переносимость произвольных сторонних headers. Конкретные SDK необходимо проверять на обеих ОС отдельно.
- Открытые страницы WG14 N1570 и POSIX были недоступны через веб-инструмент; на них не построены утверждения этого исследования. Нельзя считать эти стандарты прочитанными.

## Как проверять драфт, запускать сборку и развивать системные конвейеры?

### Takeaway

Первый рубеж — сквозное выполнение одного и того же ядра на Linux/Windows, проверяемое положительными и отрицательными примерами. Кэш и процессы добавлять после устойчивого драйвера сборки; будущий pipe не требует отдельного исполняемого файла на каждый этап.

### Cited Findings

- Rust `Command` принимает программу и аргументы отдельно и не выполняет shell splitting, globbing и substitution; документация отмечает особые правила Windows для `cmd.exe` и batch files. Это пример подходящего интерфейса драйвера независимо от выбранного языка реализации. [Rust: Command](https://doc.rust-lang.org/std/process/struct.Command.html).
- Windows `CreateProcessW` получает command-line string и отдельно имя executable; отсутствие явного имени при пути с пробелами создаёт неоднозначность. Параметры нужны для env, cwd и стандартных handles. [Microsoft: CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw).
- Nushell различает внутренние типизированные данные и байты внешних процессов; граница требует преобразования данных, тогда как между внешними процессами сохраняется обычный byte pipe. Это полезный действующий ориентир, а не доказательство оптимальности семантики для lac. [Nushell: Pipelines](https://www.nushell.sh/book/pipelines.html).

### Inferences

**Предлагаемая последовательность, без выдуманных сроков:**

1. Зафиксировать исполнимый контракт минимального ядра: grammar, типы, порядок вычислений, ошибки, entry point, supported FFI. Утвердить небольшой corpus эталонов с ожидаемым stdout, exit code, типом результата и ошибками.
2. Сделать frontend и C emission для чисел, bool, блоков, статических функций и условий. Драйвер создаёт отдельную временную папку, сохраняет исходник/C, вызывает C-компилятор, запускает результат только при успешной сборке. Выдать отдельную ошибку при отсутствующем toolchain.
3. Сделать импорт и `puts` через явное преобразование строки; проверить собственный header и функцию из отдельно скомпилированной C-библиотеки. Unsupported API отказывает до генерации.
4. Добавить структуры по значению, heap-конструкторы и выбранный runtime/GC; затем массивы, замыкания, sequence и `.collect`. Раньше heap-объектов нужен контракт времени жизни и корней.
5. Добавить редактор на основе тех же токенов/позиций и модели символов. Редактор обязан терпеть незавершённый исходник; строгий parser сборки и восстановление ошибок могут быть разными режимами общего фронтенда.
6. После первого драфта — файловые API, процессы, typed/byte pipeline adapters. `grep` остаётся установленной системной программой. Языковые этапы внутри одного executable могут передавать структуры без сериализации, внешние процессы требуют bytes. Раздельный процесс для этапа — отдельная семантика, изоляция и overhead, не следствие `|`.

Лямбды, heap-размещение лямбд, range/sequence, сохранение состояния `.next`, `.collect` и строки уже относятся к обсуждавшимся требованиям. Порядок выше означает внутренние вехи разработки, а не удаление этих требований из драфта. Если предлагается выпускить «нулевой прототип» только с typed core + C emission и FFI, его надо отдельно назвать ограниченным подэтапом и согласовать, а не объявлять весь первый драфт завершённым. Готовность стадий проверяется так: frontend — ожидаемые AST/типы и негативные диагностики; C core — сквозное выполнение на обеих ОС; FFI — реальный header + реальная linked function; runtime — agreed lifetime cases; sequence — точные значения и исчерпание; готовый драфт — весь согласованный corpus через file/CLI и temp run.

**Минимальные критерии приёмки:**

- `sum(a:i,b:i):i{a+b}` и выражение условия дают одинаковое наблюдаемое поведение на Linux/Windows, при `-O0`/`-O2`.
- Положительные и отрицательные примеры регистров размещения: `p=point(...)`, `P=Point(...)`, ошибка `p=Point(...)`. Проверить отсутствие возврата адреса завершившего жизнь локального объекта.
- Таблица строк включает `f("a","b")`, `f("a,"b)`, escaped comma, кавычку, `$`, backslash, пустую строку, скобки внутри полной строки и соседний вызов на следующей строке. Пока таблица не имеет однозначных ожидаемых AST, grammar нельзя считать готовой.
- При вызовах с побочными эффектами наблюдаемый порядок совпадает с выбранной спецификацией; выбранная overflow policy выдерживает оптимизацию C.
- FFI: корректный `puts`, wrong arity/type, отсутствующий header, unresolved symbol, неподдерживаемый macro/varargs, C nullable result и строка с не-ASCII содержимым.
- Исходник из файла и из явного строкового CLI-параметра эквивалентен. Путь с пробелами, кавычкой и нелатинскими символами не превращается в shell-код. Генерируемое приложение получает собственные argv отдельно от флагов компилятора.
- Программа с ошибкой lac не запускает C-компилятор; ошибка C-сборки не запускает бинарник. Диагностика указывает исходную позицию lac; режим отладки сохраняет C.
- Для памяти отдельные тесты: surviving closure, вложенный объект, цикл, многократная `.collect`; поддерживаемость случаев зависит от выбранного GC, а не обещается заранее.

**Предлагаемый CLI:** явные режимы `lac run file.lac`, `lac build file.lac -o result`, `lac eval 'source'`, `lac emit-c file.lac`. Это только предложение наряду с утверждённой целью `>>`. Внешняя shell обрабатывает `>>` раньше lac, поэтому для исходника через командную строку нужен quoted single argument либо иной явный ввод. Внутри файла `>>` можно обрабатывать как часть lac, если сохраняется этот синтаксис.

**Кэш:** сначала кэшировать бинарник, а не эффект выполнения. На каждый run исполнять приложение заново. Ключ включает bytes исходника/модулей, version/options compiler lac, runtime revision, target/ABI, C compiler identity/version/flags, transitively used headers с define/include configuration, linker configuration и linked libraries. Environment/cwd приложения влияют на выполнение, не обязательно на binary key; environment, влияющее на C-сборку, учитывать. Зависимости получать через toolchain, запись кэша делать атомарно, concurrent builds разводить по отдельным directories. Полный hermetic build — более поздняя задача.

### Gaps

- Конкретная syntax CLI не утверждена. Нельзя обещать unquoted one-liner с `|`/`>>` одинаково во всех shell.
- Кэш непрост для изменяемых библиотек, system headers, toolchain search paths и build environment. Простой hash исходника не гарантирует эквивалентный бинарник.
- Windows/Linux process semantics и статус конвейера ещё не выбраны; POSIX-страницы открыть не удалось. В будущей работе нужны backpressure, отмена, stderr, раннее завершение потребителя и правила cleanup.
- Отдельный object file нельзя непосредственно исполнять как процесс: потребуются линковка в executable или загрузка в runtime. Для linkable разделения модулей нужен ABI, для отдельных процессов — формат межпроцессных данных. Выбор пока открыт.
