# Синтаксис, типы и Unicode lac: исследовательские заметки

Дата: 2026-10-01. Прочитаны AGENTS.md, MEMORY.md, docs/language.md, docs/draft-01.md, docs/roadmap.md. Все рекомендации ниже — предложения для обсуждения, а не изменения утверждённых требований. Коммитов и изменений спецификации не выполнялось. Источники открыты в полном тексте; изучены релевантные определения и разделы, а не только результаты поиска. География определяется указанными авторами учреждениями, не гражданством автора.

## Как сделать компактную грамматику однозначной и пригодной для редактора?

### Takeaway

Главный блокер — не выбор парсера, а отсутствие правил различения закрытой строки и сокращённой строки. Можно сохранить компактность, но режим литерала должен определяться локально или иметь точно заданное правило приоритета; PEG не угадывает намерение автора.

### Cited Findings

- PEG выбирает первую успешную альтернативу: порядок правил меняет язык. Мемоизация позволяет построить линейный распознаватель; исходная формализация требует исключить прямую и взаимную левую рекурсию в корректных грамматиках. Это не утверждение, что любой написанный вручную рекурсивный парсер автоматически линейный. — [Ford, полный текст, §§2–3.6](https://pdos.csail.mit.edu/~baford/packrat/popl04/peg-popl04.pdf).
- Проверка результата по дереву разбора сама по себе не устанавливает полноту и однозначность. Jourdan, Pottier и Leroy проверяют соответствие LR(1)-автомата грамматике; лексический анализ, проверка типов и elaboration остаются отдельными обязанностями фронтенда. — [Validating LR(1) Parsers, введение и §§3–5](https://gallium.inria.fr/~fpottier/publis/jourdan-leroy-pottier-validating-parsers.pdf).
- Авторы французского проекта описывают практическую проблему контекстно-зависимого C-лексера: сложность в лексере может подорвать гарантии проверенного парсера. Это полезная инженерная аналогия, не доказательство сложности именно lac. — [Jourdan, 2012](https://cambium.inria.fr/blog/verifying-a-parser-for-a-c-compiler/).

### Inferences

**Утверждено:** `f("a","b")` равно `f("a,"b)`; `f("a,b")` содержит один аргумент; сокращённую строку завершают `) } ] ,`, кроме экранированных; явно закрытая строка может содержать эти знаки.

**Конкретный конфликт простой стратегии:** правило «первый разделитель завершает строку» ломает `f("a,b")`; правило «следующая кавычка закрывает строку» ломает `f("a,"b)`, потому что второй открывающий знак принимается за закрывающий первого литерала. Экранирование не решает различение двух режимов, пока пользователь одновременно допускает неэкранированную запятую внутри явно закрытой строки. Это не доказательство невозможности парсера: можно задать глобальную стратегию выбора, но её ещё нет в требованиях.

**Редакторский контрпример:** `print("a); print("b)` задумано как два вызова с сокращёнными строками. Поиск будущей кавычки вместо локального окончания меняет классификацию всего промежутка. Дописывание кавычки далеко справа может менять старую подсветку. Для первого драфта нельзя обещать стабильную подсветку до выбора правил.

**Ранжирование предложений:**

1. P0, лучший для MVP: обычные строки требуют закрывающей кавычки; сокращённая форма имеет отдельный локальный маркер, например `~"hello)`. Маркер только иллюстрация, не готовое решение. Сохраняются короткие строки, но меняются исходные примеры. Можно отложить сокращённую форму, пока компиляторное ядро работает.
2. P1: сохранить исходные формы, но формально определить scannerless PEG, порядок альтернатив, предел просмотра, EOF/newline, recovery. Проверить весь корпус эталонных строк; показать пользователю, как правило влияет на примеры. Цена — контекстная подсветка и больше негативных тестов.
3. Не рекомендую «пробовать варианты до того, пока получится валидная программа» как неописанное правило. Тогда соседний код/перегрузки могут выбирать значение литерала; при нескольких допустимых разборах нужен дополнительный порядок.

**Интерполяция:** оставить `$name` и `$name.field`, а для вызовов/выражений предложить `${expr}`. Это отдельное предложение: сейчас `${...}` не утверждено. Ограничить short-form локальной цепочкой полей, чтобы `$obj.method()` не конфликтовало с закрывающей строку `)`. Уточнить escape-порядок: `\$` — текст, `${...}` — другой режим разбора со своей вложенностью. Составить таблицу `\"`, `\\`, `\,`, `\)`, `\]`, `\}`, `\n`, `\r`, `\t`; часть последних escapes ещё не утверждена. В regex и путях особенно полезен будущий сырой литерал.

**Другие точки грамматики:**

- `1..9` должен разбираться до попытки принять `1.` за дробное число. Дробное число в MVP может требовать цифру после точки. `0...size` — ровно `INTEGER RANGE DOT IDENT`, не оператор `...`.
- Имя без цифр делает `(a1..9)` разложимым, но `a:i=3 b:i=4` требует правила разделения объявлений. Предлагаю newline/`;` как разделители, запятую — только внутри списков. Это немного длиннее однострочного исходника, но снимает неявное завершение выражения.
- Не утверждать, что запрет цифр необходим для компактного обхода. Альтернатива `(a:1..9){...}` добавляет один знак и позволяет в будущем `sha256`, `http2`, номера переменных. В MVP можно сохранить утверждённый запрет, отдельно разрешив зарезервированные имена типов `i32/u32` и импортированные C-имена.
- Блок `{expr}` и closure `{expr}` надо различать контекстом либо явной полной формой `():T{expr}`. Sequence `{0..5}` нуждается в отдельном typed AST-узле; обычная лямбда, повторно возвращающая один Range, ещё не является состоянием итератора.
- `.` разрешать как ссылку на единственный ближайший неименованный аргумент; вложенные лямбды с внешним доступом обязаны именовать аргументы. Это позволит lowering в обычные имена без «магического» динамического scope.
- Первый вызов `point(x=...,y=...)` может вводить номинальный тип лишь в заранее определённой lexical scope; определение формы нельзя ставить в зависимость от того, какая ветвь исполнится первой. Для MVP рекомендую явное `point{x:d,y:d}` перед конструктором, оставив совместную форму поздним сахаром.
- Точка входа «первая функция» означает, что добавление helper-функции в начало меняет исполнение. Предлагаю явные `main()` или `m()` для файла, неименованный вход только для отдельного режима командной строки.

### Gaps

- Не выбран предел поиска закрывающей кавычки, поведение EOF/newline, полный escape-набор и граница интерполяции. Научные статьи не могут выбрать эти правила вместо автора lac.
- Не определены function-value reference при вызове метода без скобок, ранний return, разрешение рекурсии, импорт имён с цифрами.
- Сокращённые формы обхода пока не имеют эталонных AST и типов результатов; их проверка должна предшествовать оптимизации парсера.

## Какие правила типов и C-понижения нужны для предсказуемого первого драфта?

### Takeaway

Генерация C не требует наследовать всю семантику C. Лучшее практическое направление — типизированное ядро lac с локальным выводом, явно определёнными числовыми преобразованиями и порядком вычисления; затем независимое понижение в C.

### Cited Findings

- Bidirectional typing разделяет синтез типа по выражению и проверку выражения относительно известного типа. Обзор выделяет локальность ошибок, предсказуемость и стабильность аннотаций; авторы отмечают, что лёгкость измерить количество аннотаций не делает их количество единственным важным критерием. — [Dunfield/Krishnaswami, §§1–4](https://research.cs.queensu.ca/home/jana/papers/bidir-survey/Dunfield21_bidir-survey.pdf).
- C определяет обычные арифметические преобразования, включая переход signed/unsigned; преобразование скаляра в bool использует ноль/неноль. Непредставимый арифметический результат может давать undefined behavior; функции/выражения имеют собственные правила sequencing. Точные `intN_t` и `uintN_t` задаются в `<stdint.h>` при наличии соответствующих типов реализации. — [WG14 N3096, §§6.3.1.2, 6.3.1.8, 6.5, 7.22.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3096.pdf). Это рабочий проект 2023 года, не заявление о последней редакции ISO.
- Kotlin различает generic `Array<T>` и primitive arrays; generic array примитивов требует boxing на JVM. Изменяемые массивы инвариантны; выход за границу вызывает исключение. У lac уже выбрана другая модель хранения, которую не следует называть точной копией Kotlin. — [Kotlin Arrays](https://kotlinlang.org/docs/arrays.html).
- Wadler/Findler исследуют взаимодействие более и менее типизированных компонентов через явные casts и blame. Теорема относится к их формальному исчислению, а не доказывает безопасность произвольного C FFI. — [Well-typed programs can’t be blamed, §§2–4](https://homepages.inf.ed.ac.uk/wadler/papers/blame/blame-tr.pdf).

### Inferences

**P0 — таблица типов:** утвердить типы литералов, арифметических операций, сравнения, `?:`, конструкторов, `.{}`, `.collect`, индексации. Пример `a:d=3` можно проверить по ожидаемому `d`, а `a=3` синтезирует стандартный целочисленный тип. Для рекурсивных функций MVP требует сигнатуру аргументов и результата; лямбда может брать тип параметров из контекста. Полную Hindley–Milner/overload inference пока не обещать.

**P0 — bool:** `d:b=1` допускается требованием пользователя, но если разрешить все C-подобные numeric→bool conversions везде, требование «условие принимает только bool» станет практически пустым. Рекомендую либо разрешить 0/1 только в явной инициализации `:b`, либо потребовать `b(value)` для остальных случаев. Это изменение/уточнение требует согласования, не уже принятое правило. `and/&&` и `or/||` — одинаковые bool-операторы с short-circuit; `xor` вычисляет оба bool. Битовые операции отдельно; `|` зарезервировать будущему pipe.

**P0 — signed/unsigned:** контрпример C-подобной таблицы `a:i=-1; z:u=1; a<z`: при общей unsigned-форме отрицательное число превращается в большое положительное. Сохранять «как C» можно, но нужно явно принять этот результат и диагностику. Лучшее предложение — неявные преобразования только без потери диапазона; mixed signed/unsigned с непокрываемым диапазоном требуют конструктора. `i64→d` тоже не всегда точное преобразование, хотя destination «больше»: 64-битные целые превосходят точную мантиссу double.

**P0 — арифметика:** выбирать checked overflow по умолчанию (контролируемая ошибка lac), explicit wrapping как будущую операцию. Вариант wrapping по умолчанию тоже реализуем, но должен быть одинаковым на Linux/Windows. Не выводить raw signed C `a+b`, если lac обещает wrapping: UB позволяет C-компилятору менять поведение. Даже только проверки division by zero недостаточно — минимум signed / -1 и сдвиги тоже требуют правил.

**P0 — порядок:** рекомендую аргументы слева направо и ровно одно вычисление получателя/аргумента. В C lowering сначала создать temporaries, затем вызвать функцию. Иначе `sum(seq.next,seq.next)` может зависеть от C toolchain. `?:` вычисляет одну выбранную ветвь.

**P0 — имена и размещение:** сохранить утверждённые `p=point(...)`, `P=Point(...)`, запрет `p=Point(...)`, исключение `seq={}`. Но регистр имени должен быть проверяемым сахаром над явным типом value/ref, не единственной причиной ABI/layout. Не считать `A=3` совместимым с примитивом «по значению» без фиксации типа результата: `A` — pointer handle, его объект в куче; `i` и `I` имеют разные операции/преобразования.

**P1 — развитие размещения:** предпочтительная долгосрочная модель «value/ref — семантика; физическое stack/heap — оптимизация при сохранении наблюдаемого поведения». Это меняет буквальное требование размещения и должно быть согласовано. Названия не должны мешать безопасному spill/return больших массивов. Для MVP не делать автоматическое поднятие stack-value в heap: лучше запретить небезопасный escape с ясной диагностикой.

**P0 — массивы и коллекции:** inline-массив `point` и `Array<Point>` могут сосуществовать; явно определить generic element type, копирование inline value и равенство. Размер элемента и расположение буфера — разные решения: массив миллионов inline objects может находиться в heap. Для mutable контейнеров в MVP инвариантность проще безопасной ковариантности. `.cp` копирует внешнюю структуру и сохраняет ссылки на вложенные объекты; `.dpcp` требует map старых адресов→новых, чтобы сохранять sharing и циклы, а не наивной рекурсии.

**P0 — отсутствие значения:** запрет null в Map не исключает отдельный результат «ключа нет». Тип `Option<T>` или tagged result нужен компиляторному ядру, даже если пользовательский сахар остаётся `getIfPresentOr`/`next?{...}`. Не скрывать возвращаемый тип за исключением: нормальное завершение sequence — не аварийное состояние памяти.

### Gaps

- Не определены numeric conversions lac при смешанных типах, литералы, overflow, short-circuit словесных операторов, equality/identity, тип результата копирования.
- FFI не может перенять гарантии доказанной типовой системы одной ссылкой на статью. Заголовки C описывают ABI-типы, но не весь контракт владения, nullable, bounds и effects.

## Как определить строки без потери системной направленности языка?

### Takeaway

UTF-16 — утверждённый выбор, его не следует молча менять. Однако «символ» нужно разделить на кодовую единицу, Unicode scalar и grapheme; байтовый ввод/вывод и пути должны иметь отдельные контракты. Рассматривать UTF-8 как альтернативу развития разумно, но обещать универсальное ускорение без измерений нельзя.

### Cited Findings

- Unicode определяет UTF-8 кодовые единицы по 8 бит, UTF-16 — по 16; supplementary scalar в UTF-16 представлен surrogate pair. Изолированные surrogate units не являются корректно сформированным Unicode scalar. — [Unicode 16, глава 3, §§3.8–3.9](https://www.unicode.org/versions/Unicode16.0.0/core-spec/chapter-3/). Версия зафиксирована для цитирования определения, не названа последней.
- Один воспринимаемый символ может состоять из нескольких code points. UAX #29 задаёт grapheme boundaries, приближающие пользовательское восприятие, и подчёркивает отличие такого количества от размера данных. — [UAX #29, revision 49, 2026-09-01, §3](https://www.unicode.org/reports/tr29/tr29-49.html).

### Inferences

**P0 — сохранить UTF-16, назвать единицы:** `c` = 16-bit code unit; `s.size` = число code units; дополнительные `codePoints`/`graphemes` позже. Это предложение детализации, ещё не подтверждённое автором. Контрольные примеры: `A` — 1 unit/1 scalar/1 grapheme; `😀` — 2/1/1; `e` + combining acute — 2/2/обычно 1. Диапазон char и произвольная индексация могут образовать unpaired surrogate: решить, может ли `c[]` быть сырым буфером, а `S(buffer)` обязан валидировать UTF-16.

**P0 — иммутабельность:** `s=chars.toS` обязана копировать mutable buffer либо передавать его владение с запретом дальнейшей мутации. Общий указатель на тот же изменяемый массив не обеспечивает immutable string. Строка лучше иметь собственный runtime type, даже если пользовательские операции похожи на массив.

**P0 — потоки:** входной `(s)` «весь вывод lazy» не тождествен обычной индексируемой строке. `.size` на незавершённом stdout требует дождаться EOF/материализовать. Предлагаю будущий отдельный `Stream<bytes>`/`Sequence<s>` для lines и явное получение `s`. Первый драфт без pipe может не реализовывать этот тип вообще.

**P1 — UTF-8 как альтернативная стратегия:** invariant-valid UTF-8 string удобна для ASCII-heavy текста и byte interfaces; индекс по scalar становится не O(1). UTF-16 сохраняет знакомые операции и может быть удобна для некоторых платформенных интерфейсов; всё равно требует conversion. Это инженерные гипотезы по представлению, не benchmark. Нельзя определить Unix path произвольных байтов только как «валидный Unicode»: отдельный Path/bytes контракт нужен независимо от кодировки.

### Gaps

- Единица размера и индексации ещё не утверждена; Unicode не определяет lac API. Не проверялись платформенные filesystem contracts в рамках этого подзадания, поэтому конкретные утверждения Linux/Windows следует брать из исследования системного слоя.
- Не выбраны malformed decoding policy, NUL внутри строк для C, regex engine и единица позиции совпадения; без этого нельзя обещать прозрачный FFI.
