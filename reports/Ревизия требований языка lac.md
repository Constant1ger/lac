# lac: укрепить семантику, сохранив краткость языка

> Исторический исследовательский отчёт до последнего ответа автора. Последующие решения: закрытые ASCII-строки, направление без GC, новые `fe`, трансформация и операторы. Актуальные требования — [ревизия 2](../docs/revision-02.md); варианты памяти — [без GC](../docs/memory-without-gc.md). Рекомендации GC/строк ниже не являются действующей спецификацией.

Дата исследования: 1 октября 2026 года. Статус: исследовательская ревизия и предложения для обсуждения. **Ни одно предложение этого отчёта не изменяет утверждённую спецификацию без решения автора языка.**

**Лучшее направление для lac — сохранить генерацию C, но сначала определить небольшое типизированное ядро, в которое понижаются краткие конструкции.** Основной риск первого компилятора сейчас связан с неоднозначными строками, временем жизни объектов, состоянием sequence и границей C, а не с отсутствием собственного машинного бэкенда. Для Linux и Windows предлагается переносимое подмножество C17, собственный фронтенд, небольшой runtime и проверяемые примеры с одинаковым поведением на обеих ОС. Для желаемого освобождения недостижимых графов наиболее последовательный вариант — точный неперемещающий mark-and-sweep; готовый консервативный GC пригоден как ускоритель экспериментального прототипа. Простое RC не покрывает циклы, а реальные нарушения памяти не должны служить механизмом обычных ошибок языка. Краткость можно сохранить через сахар над обычными вызовами, лямбдами и итераторами; способы сокращения строк и имя как признак размещения требуют отдельного решения. Pipe и внешние команды остаются за пределами первого драфта, как уже выбрал пользователь.

## 1. Первый драфт требует согласования семантики, а не нового бэкенда

### Что уже выбрано и что остаётся предложением

Проектные документы задают самостоятельный строго типизированный язык для файлов и системных утилит, вдохновлённый Bash и Kotlin. Первый драфт предназначен для Linux и Windows, переводит собственный код lac в C и предоставляет явный импорт конкретных `.h`. Он принимает файл или исходник из командной строки. **Последнее уточнение пользователя: сейчас результат компиляции сохраняется в файл с заданным названием либо в `a.exe`; temp-run и кэш имеют низкий приоритет P2.** Имя `a.exe` пока принято по умолчанию и для Linux, без самостоятельной замены на `a.out`; синтаксис флага ещё не выбран. Работа с `grep`, pipe, БД и HTTP относится к дальнейшему развитию. Источники не дают оснований менять эти границы: C — уже принятое решение, а переход к LLVM или интерпретатору сейчас лишь добавит работу.

Приняты примитивы фиксированной ширины, инициализация при создании, отсутствие присваиваемого `null`, функции как значения, структуры и конструкторы, UTF-16 и иммутабельные строки. Обычные массивы содержат объекты непосредственно, коллекции `Array`, `Map` — ссылки на объекты, а примитивы везде сохраняются по значению. Это собственная модель lac. Называть её точной моделью Kotlin некорректно: Kotlin различает generic arrays и специальные primitive arrays, а generic array примитивов на JVM связан с boxing. ([Kotlin: Arrays](https://kotlinlang.org/docs/arrays.html).)

Подсчёт ссылок был ранней идеей; последнее пожелание — освобождать объект, когда до него нет пути от активных корней через граф ссылок. Это семантическая цель, алгоритм ещё не выбран. Также не выбраны окончательная грамматика сокращённых строк, переполнение, захваты изменяемых переменных, результат `.collect`, завершение iterator и полный FFI. Rust-подобное управление памятью было ориентиром; обязательного borrow checker сейчас нет. Нельзя объявлять готовность этих частей только по аналогии с известным языком.

В документах остаются исторические формулировки. Например, `P=point(...)` сохранён как исходный пример, но позднее согласован `P=Point(...)`; раннее `pnt=Point(p)` противоречит последнему правилу и заменено на `Pnt=Point(p)`. Рекомендация — помечать такие места как историю и ссылаться на последний контракт, сохраняя авторские примеры. Этот отчёт сам не переписывает действующие требования.

### Приоритеты ревизии

P0 означает решение перед реализацией соответствующего ядра; P1 — перед полноценным драфтом или расширением; P2 — развитие после сквозного прототипа. Это приоритет зависимости, а не оценка важности идеи.

| Приоритет | Текущее требование или пробел | Риск | Предлагаемое решение, ещё не утверждённое |
|---|---|---|---|
| P0 | Закрытая и сокращённая строка начинаются одинаково | Один локальный алгоритм не удовлетворяет всем примерам | Выбрать явный режим сокращения либо формальную стратегию выбора разбора |
| P0 | Объявления рядом без заданного разделителя | Парсер не знает границу выражения | Перевод строки/`;` между выражениями; запятая внутри списков |
| P0 | C-преобразования и строгое bool-условие | Неявный numeric→bool обесценивает ограничение | Отдельная таблица преобразований и контекстов |
| P0 | Нет правила переполнения и порядка аргументов | Поведение меняется после C-оптимизации | Checked arithmetic, вычисление слева направо |
| P0 | Регистр задаёт стек/кучу; `seq={}` — исключение | Неясны реальные типы и результаты `.cp` | Внутренне различать value/ref/function; регистр проверять отдельно |
| P0 | Java-подобная достижимость без алгоритма | RC удерживает циклы; C не знает managed-корни | Выбрать GC и root protocol до heap-объектов |
| P0 | `{}` одновременно block/lambda/sequence | Лямбда, возвращающая Range, не обязана быть счётчиком | Отдельные AST-узлы, Iterator с состоянием |
| P0 | `.next` при исчерпании и ошибки не разделены | Штатное завершение становится аварией | Внутренний `Item / End / Error`, контролируемый panic |
| P0 | Автоматический доступ через импорт `.h` | `#include` не даёт фронтенду lac типов | Clang для деклараций и опубликованный поддерживаемый FFI |
| P0 | Точка входа — первая функция | Helper или импорт меняет запуск | Явный `main`/`m` для файлов; отдельное правило короткого режима |
| P1 | UTF-16 называется символами | Emoji и комбинируемые знаки дают неожиданную длину | Назвать code-unit length; добавить другие обходы позднее |
| P1 | `.collect` не задаёт контейнер | Изменяется хранение и идентичность объектов | Тип результата/целевой контейнер задавать явно |
| P1 | `.dpcp` универсален | Циклы и ресурсы не копируются простой рекурсией | Memo-table для графов; ограничения для внешних ресурсов |
| P1 | Объект индексируется как массив | Разные поля имеют разные типы | Constant index/tuple либо явный sum type для динамического доступа |
| P1 | Редактор открывается при `lac` | Незавершённый ввод ломает строгий разбор | Общие токены/позиции, отдельный режим восстановления |
| P2 | Кэш по хэшу исходника | Изменившийся header/toolchain не меняет ключ | Кэш бинарника с зависимостями сборки |
| P2 | Прежний temp-run без флага | Увеличивает объём первого драфта | По новому решению отложить; сейчас output name либо `a.exe` |
| P2 | Каждый pipe-этап — отдельный object file | Object file не запускается сам; процессы требуют протокола | Разделить модули, вычислительные этапы и процессы |

### Что научные работы действительно дают проекту

Работа LLVM описывает независимое от исходного языка промежуточное представление для анализа и преобразований. Для lac отсюда следует полезность границы между фронтендом и генерацией, но не необходимость внедрять LLVM, SSA и оптимизатор в первом драфте. Исследование CompCert показывает роль промежуточных языков и сохранения наблюдаемого поведения; оно также напоминает, что даже несложные преобразования требуют аккуратности. Использование C-компилятора не доказывает правильность переводчика lac. ([Lattner и Adve, CGO 2004](https://llvm.org/pubs/2004-01-30-CGO-LLVM.html); [Leroy, CACM 2009](https://xavierleroy.org/publi/compcert-CACM.pdf).)

## 2. Краткость работает, когда разбор и типы предсказуемы

### Сокращённые строки требуют самостоятельной грамматики

Утверждённые примеры необходимо сохранить в корпусе требований:

```plaintext
f("a","b")
f("a,"b)
f("a,b")
print("a); print("b)
```

Первые две строки должны давать два аргумента; третья — один с запятой; последняя показывает два соседних вызова с сокращёнными литералами. **Правило «заканчивать при каждой запятой» ломает третью запись, а «брать следующую кавычку» ломает вторую.** Экранирование решает включение знака в короткий литерал, но не определяет, какой режим выбрал автор при общей открывающей кавычке. Это не доказательство невозможности языка: недостаёт правила приоритета, предела просмотра и обработки нескольких допустимых разборов.

Лучший для быстрого MVP вариант изменения — обычная закрытая строка и отдельно маркированная сокращённая, например `~"hello)`. Маркер здесь только иллюстрация, **синтаксис не утверждён**. Второй вариант — сохранить все формы и точно задать контекстную грамматику, включая EOF, перевод строки, вложенную интерполяцию и recovery. Третий, самый рискованный — перебирать варианты до «валидной программы» без опубликованного порядка: соседний код начинает выбирать содержимое литерала.

PEG разрешает выбор порядком альтернатив, но этот порядок сам является частью языка. Packrat-мемоизация обеспечивает линейное распознавание при соответствующих предпосылках; произвольный самописный рекурсивный парсер не получает это свойство автоматически. Европейская работа по проверке LR(1)-парсеров показывает другую сторону: соответствие автомата грамматике не заменяет определение лексики и семантические проверки. Выбор PEG, LR или recursive descent должен следовать после согласования примеров. ([Ford, POPL 2004](https://pdos.csail.mit.edu/~baford/packrat/popl04/peg-popl04.pdf); [Jourdan, Pottier и Leroy, ESOP 2012](https://gallium.inria.fr/~fpottier/publis/jourdan-leroy-pottier-validating-parsers.pdf).)

Для интерполяции предлагается сохранить `$name` и `$name.field`, а произвольные выражения поместить в `${expr}`. Это изменение требует одобрения. Вызов внутри короткой формы конфликтует с `)`, который завершает литерал; явная граница выражения делает правила проще. Нужна таблица реальных символов исходника для кавычки, backslash, `$`, скобок и запятой, отдельно от JSON/Markdown-экранирования. Для путей и regex позже полезен сырой литерал, но он не нужен для первой арифметической программы.

Запрет цифр в именах помогает разобрать `(a1..9)`, однако мешает привычным `sha256`, `http2` и именам C. Для MVP можно сохранить запрет переменных и предусмотреть отдельный импортный namespace/alias. Долгосрочная альтернатива — `(a:1..9){...}`, освобождающая обычные имена; она не утверждена. В лексере `1..9` должен распознаваться как диапазон, а не дробное `1.`; `0...size` — число, `..`, точка и `size`. Никакого оператора из трёх точек пользователь не вводил.

### Малым набором правил можно покрыть многие сокращения

Предлагаемое семантическое ядро включает значения и ссылки, локальные объявления, функции, вызовы, блоки, условное выражение, структуры, массивы, итератор и ошибки. `obj.method(x)` понижается в обычный вызов с получателем, `.next` — в `.next()`, `arr(1..9).+1` — в выбор элементов и map-лямбду. Точка превращается в имя конкретного аргумента ближайшего контекста. Такие сокращения не требуют новых фундаментальных механизмов исполнения.

При этом heap-объекты, захваты, stateful iterator, преобразования строк, GC и FFI действительно требуют runtime или явного низкоуровневого кода. Не всё можно реализовать заменой текста. `.{}` сейчас означает поэлементный обход, а `(a1..9){...}` возвращает результаты; нужно определить, когда операция является map, когда forEach и какой у неё результат. `[..]` уже утверждён как forEach, его нельзя молча объявить slice. Вложенная точка должна ссылаться на ближайший анонимный аргумент; доступ к внешнему аргументу лучше требовать через имя.

Для `point(x=4.4,y=5.1)` следует фиксировать форму типа при анализе lexical scope, а не при первом реально исполненном вызове. Иначе две ветви с разными полями делают тип зависимым от исполнения. Более простой MVP-вариант — явное `point{x:d,y:d}` перед вызовом, но это предложение изменить совместное определение/создание. Индексирование структуры с полями разных типов требует отдельного контракта: `obj[0]` с известным индексом можно типизировать как поле, но `obj[index]` не имеет одного обычного типа без варианта, boxing или ограничения однородности.

Правило «первая функция — вход» конфликтует с helper-функциями и потенциальными импортированными объявлениями. Рекомендуется для файлов явный `main()` или `m()`, а для короткой CLI-программы один анонимный entry point. Если сохраняется прежнее правило, нужно как минимум ограничить его только верхнеуровневыми функциями текущего исходника и диагностировать неоднозначность. Также необходимо задать тип возврата entry point и его связь с exit code.

### C-подобные преобразования требуют точной таблицы

Сигнатура `sum(a:i,b:i):i{a+b}` хорошо подходит локальному выводу: выражение синтезирует тип, а явная аннотация задаёт ожидаемый. Двунаправленная проверка типов позволяет разделять эти операции и получать локальные ошибки. Это практичная стратегия, не требование сразу внедрять полный алгоритм вывода полиморфных типов. Для рекурсивных функций разумно требовать сигнатуры; для лямбд использовать ожидаемый тип из контекста. ([Dunfield и Krishnaswami, ACM Computing Surveys 2021](https://research.cs.queensu.ca/home/jana/papers/bidir-survey/Dunfield21_bidir-survey.pdf).)

Контрпример текущему направлению преобразований:

```plaintext
a:i=-1
z:u=1
a<z
```

При C-подобном переходе к общему unsigned-типу сравнение даёт результат, неожиданный для математических целых. Аналогично `i→d` не сохраняет все 64-битные целые точно. C отдельно определяет scalar-to-bool, арифметические преобразования и случаи undefined behavior. Это подтверждено рабочим проектом WG14 N3096; он используется как источник конкретных правил, а не объявляется последней редакцией ISO. ([WG14 N3096, §§6.3 и 6.5](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3096.pdf).)

Рекомендуемое изменение: неявно разрешать только преобразования, сохраняющие допустимые значения, а потенциально теряющие точность делать явными конструкторами. Если пользователь предпочитает буквальное «как C», нужно утвердить результаты signed/unsigned-примеров и предупреждения. Для `d:b=1` можно сохранить специальную инициализацию из 0/1, требуя `b(value)` в остальных случаях; иначе ограничение bool-условия будет обходиться автоматическим преобразованием любого числа. `and/&&` и `or/||` предлагается сделать короткозамыкающими, `xor` — вычисляющим оба операнда.

Порядок аргументов предлагается определить слева направо. `sum(seq.next,seq.next)` должен иметь одинаковый результат независимо от C toolchain; генератор создаёт промежуточные значения до вызова. Для арифметики рекомендуются проверяемые переполнение и деление, с будущими явными wrapping-операциями. Если выбрать wrapping по умолчанию, его тоже нужно реализовать явно: raw signed C `a+b` не обеспечивает такую семантику. Проверки нужны и для минимального signed числа, делённого на `-1`, и для недопустимых сдвигов.

## 3. Достижимость, sequence и ошибки образуют единый runtime-контракт

### Значение, ссылка и физическое размещение — разные свойства

Последние требования сохраняются:

```plaintext
p=point(...)
P=Point(...)
p=Point(...)  // ошибка компиляции
seq={}        // допустимое функциональное значение
```

Внутренне следует различать value-тип `point`, managed reference `Point` и функциональный тип с окружением. Сам `P` — handle, а его объект находится в куче; размещение handle отдельно от размещения объекта. Для `A=3` компилятор должен явно знать, что получается heap-примитив `I`, а не обычный `i`. Возвращаемое `:i` означает value-семантику, однако ABI вправе вернуть число через регистр. Inline-элементы большого массива могут находиться внутри heap-буфера: большое число итераций не обязательно накапливает стековые временные значения.

Рекомендация для развития — считать value/reference частью семантики, а stack/heap/register частью реализации при сохранении наблюдаемого поведения. Регистр имени тогда становится проверяемым соглашением, а не системой безопасности. Это изменение буквального размещения требует согласования. Пока можно сохранить запрет `p=Point(...)` и явно назвать `seq={}` исключением. Результаты `.cp` и `.dpcp` должны иметь определённый тип: если возвращается `Point`, маленькое имя снова должно отклоняться. Автоматический перенос стека в кучу лучше отложить: иначе нужно решать, сохраняется ли идентичность и видны ли дальнейшие изменения исходного значения.

Присваивание value копирует поля; ссылочные поля остаются ссылками. Присваивание reference копирует handle. `.cp` создаёт новую внешнюю оболочку с прежними вложенными ссылками. Для `.dpcp` нужен словарь «старый объект → новый объект»: сначала создать оболочку и зарегистрировать соответствие, затем обходить поля. Это сохраняет циклы и общих потомков. Файлы, процессы, C-handles и stateful-sequence нельзя обещать глубоко копировать универсально: клонирование ресурса требует собственного протокола.

### Почему простой RC не закрывает пожелание пользователя

Если `A` ссылается на `B`, а `B` на `A`, исчезновение внешнего владельца оставляет ненулевые RC-счётчики. Работы по сборке циклов добавляют анализ подграфов, а не просто ещё одну проверку счётчика. Perceus показывает, что тщательно вставленный RC и reuse могут быть эффективны для соответствующего функционального языка, но его garbage-free результат ограничен ациклическими программами; опубликованная реализация не предоставляет сборщик циклов. Поэтому переносить заявленную скорость Koka на lac нельзя. ([Bacon и Rajan, ECOOP 2001](https://www.researchgate.net/publication/2528969_Concurrent_Cycle_Collection_in_Reference_Counted_Systems); [Reinking и др., PLDI 2021](https://xnning.github.io/papers/perceus.pdf).)

| Место | Вариант | Почему подходит | Основное ограничение |
|---|---|---|---|
| 1 | Точный nonmoving mark-and-sweep | Соответствует достижимости, собирает циклы, стабильные адреса | Корни, descriptors, паузы, фрагментация |
| 2 | Готовый BDWGC в экспериментальном прототипе | Быстрее получить работающее generated C с GC | Консервативное удержание и внешняя зависимость |
| 3 | RC плюс сборщик циклов | Своевременное освобождение многих объектов | Два взаимосвязанных механизма, сложнее поддержка |
| 4 | Perceus-подобный оптимизированный RC | Потенциал reuse и устранения RC-операций | Зрелые анализы и подходящая семантика; не MVP |
| 5 | Rust-подобное владение/заимствования | Статическая дисциплина времени жизни | Существенное изменение модели и фронтенда |

Рейтинг отражает соответствие требованиям, а не измеренную скорость. Консервативный GC специально допускает работу с обычным компилятором без точных stack maps, но адресоподобные данные могут удерживать мусор. Это оправданный компромисс для экспериментального прототипа, если ограничения опубликованы. ([Boehm и Weiser, 1988](https://hboehm.info/spe_gc_paper/preprint.pdf); [описание BDWGC](https://hboehm.info/gc/gcdescr.html).)

Для собственного GC предлагается следующий алгоритм. Heap-объект содержит descriptor ссылочных полей и mark-bit. Генерируемая функция регистрирует frame с аргументами, локальными ссылками и живыми временными значениями; value-структуры тоже просматриваются, если содержат ссылки. В allocator располагается safepoint. Сборщик начинает от глобальных и локальных корней, итеративным worklist отмечает достижимые объекты, затем освобождает неотмеченные. Цикл без внешнего пути не отмечается. Для начальной реализации локальную ссылку можно удерживать до конца scope, позднее сократить время жизни анализом последнего использования.

Точность корней — существенная часть корректности. Даже неперемещающий объект может быть освобождён, если C-код сохраняет его адрес вне зарегистрированных корней. Руководство OCaml и исследование Boxroot показывают явные root-протоколы на FFI-границе; это полезные образцы обязательств, а не готовая библиотека для lac. ([OCaml 5.4: C interface](https://ocaml.org/manual/5.4/intfc.html); [Munch-Maccagnoni и Scherer, Boxroot 2022](https://gallium.inria.fr/~scherer/research/boxroot/2022-ml-workshop-boxroot.pdf).)

GC управляет памятью, но не заменяет своевременное закрытие файлов и источников. Нужны явные `close` и позднее scoped cleanup. Финализация не гарантирует момент нужного действия; авторское руководство Boehm рекомендует выполнять требующие своевременности операции явно. ([Boehm: Finalization](https://hboehm.info/gc/finalization.html).)

### Счётчик нельзя подменять обычной лямбдой

Предлагается различать неизменяемый `Range`, план/источник `Sequence`, конкретный изменяемый `Iterator` и однопроходный stream. Kotlin sequences бывают повторяемыми и однопроходными, могут быть бесконечными; ленивость сама по себе не обещает преимущество для малых коллекций. ([Kotlin: Sequences](https://kotlinlang.org/docs/sequences.html).)

`seq={0..5}` по пользовательскому описанию содержит сохраняемое состояние. Его можно оставить сахаром создания iterator, но обычная лямбда, каждый раз возвращающая Range, ещё не обладает cursor. Для MVP предлагается один общий cursor при копировании ссылки; независимый обход создаётся явно. Нужны точные границы и terminal-state: например, после `End` следующий вызов снова даёт `End`, не начинает диапазон заново. Это предлагаемая детализация, не принятая семантика.

В `[0...size].next` внутри преобразования счётчик может создаваться заново на каждом элементе. Размер тоже зависит от того, к чему привязана точка. Пример нумерации должен явно показать создание iterator один раз вне поэлементного тела; позднее индексированный map может стать сахаром. Конструкторы Range/Sequence не должны перемещаться оптимизацией так, чтобы изменять состояние или побочные эффекты.

Замыкание понижается в указатель на код и managed environment. Предлагаемый начальный захват: value по копии, managed reference по ссылке. Захват изменяемой переменной с общей идентичностью требует heap-cell; сырой адрес локального стека недопустим. Все пользовательские лямбды можно сохранять как heap-значения, а оптимизацию окружения без захватов обсуждать позже.

`.collect` реализуется циклом чтения: добавить `Item`, завершить по `End`, вернуть `Error` при отказе, закрыть источник на каждом пути. Нужно задавать контейнер: collection references нельзя молча разыменовывать в value-array. Примитивы не требуют boxing. Бесконечная sequence не обязана завершиться; нужны `take`, `fold`, раннее прекращение и ограничения материализации. Обещание «весь вывод lazy в `(s)`» требует отдельного контракта для случайного доступа и `.size`. Размер конечного однопроходного потока можно подсчитать с постоянной дополнительной памятью, но для этого его нужно потребить до EOF. Последующий случайный доступ или повторный обход потребует сохранения данных либо повторного чтения доступного источника; один подсчёт размера накопления всего содержимого не требует. Рекомендуется отдельный byte stream или sequence строк с явным преобразованием в `s`; это изменение входного контракта отложенного системного слоя.

### Конец последовательности — не ошибка памяти

Для внутреннего протокола предлагается `Next<T,E> = Item(T) | End | Error(E)`. Для поиска достаточно отдельного варианта отсутствия; он не является присваиваемым `null` и не требует хранить `null` в `Map`. Контракт Rust Iterator показывает этот принцип через `Option<Item>`, хотя lac может выбрать более строгие правила повторного чтения после конца. ([Rust: Iterator](https://doc.rust-lang.org/stable/core/iter/trait.Iterator.html).)

`getIfPresentOr(key,fallback)` должен вернуть найденный `V` либо один раз вызвать лямбду, возвращающую `V`. Handler, только печатающий текст, не подходит для присваивания числу. `value=seq.next?{...}` пока смешивает конец, отказ операции и bool-ветвление. Лучшие варианты — отдельный метод вроде `nextOr{value}` либо `?{}` только для Result с самостоятельным правилом End; оба варианта не утверждены.

**Настоящий SIGSEGV или Windows access violation нельзя рекомендовать для штатной ошибки lac.** Предлагается контролируемый panic с причиной, позицией исходника и ненулевым статусом. Нормальный End не вызывает panic; принудительное извлечение после конца может его вызвать. Для MVP явные error-results проще совместить с C и cleanup, чем полноценное unwinding. Если позднее нужны исключения, необходимо определить освобождение GC-корней и ресурсов на каждом пути; произвольный `longjmp` этого не обеспечивает. RustBelt показывает, что безопасность зависит от контрактов unsafe-компонентов; название модели или язык реализации не переносит доказательство на lac. ([Jung и др., POPL 2018](https://plv.mpi-sws.org/rustbelt/popl18/paper.pdf).)

## 4. C-бэкенд должен сохранять правила lac и явную границу FFI

### Рекомендуемая архитектура и её альтернативы

На первом месте — собственный фронтенд, типизированное представление и генерация C. На втором — прямой AST→C для очень ограниченной демонстрации, если уже проверены типы и порядок вычисления; разрастание текстовых специальных случаев быстро ухудшит поддержку. На третьем для будущего развития — LLVM после устойчивой семантики и измерений ограничений C. Собственная генерация машинного кода сейчас занимает последнее место: ABI, регистры и форматы файлов не решают существующих блокеров. Интерпретатор полезен как будущая эталонная модель для сравнительных тестов, но не обязателен и не заменяет выбранный драфт.

```text
исходник → токены/позиции → AST → разрешение имён и проверка типов
         → типизированный HIR → небольшое нормализованное IR → C
         → C-компилятор/линкер → исполняемый файл
```

HIR хранит разрешённые имена, типы и связь с исходником; небольшое IR делает явными temporaries, порядок вычисления, ветвления, heap-аллокации, корни и runtime-вызовы. Эти слои можно реализовать несколькими компактными структурами, без отдельной платформы оптимизаций. Статические функции становятся C-функциями; замыкания — кодом плюс окружением; iterator — состоянием плюс `next`. Нужен версионированный runtime с платформенными адаптерами.

Предлагается C17 без GNU nested functions, statement expressions и зависимости от VLA. GCC поддерживает несколько стандартов, а режим по умолчанию меняется; MSVC документирует C11/C17 с соответствующим инструментарием. Следовательно, нужно явно выбирать стандарт и публиковать проверенные версии GCC/Clang/MSVC. Поддержка двух ОС не означает готовую кросс-компиляцию. ([GCC: Standards](https://gcc.gnu.org/onlinedocs/gcc/Standards.html); [Microsoft: C11/C17 support](https://learn.microsoft.com/en-us/cpp/overview/install-c17-support?view=msvc-170).)

Rust — подходящий кандидат для реализации фронтенда при знакомстве автора с ним; C++ удобен при глубокой интеграции с Clang. Лучший выбор определит небольшой технический эксперимент импорта и codegen, а не общее сравнение языков. Generated C следует сохранять в отладочном режиме, дополнять `#line` и картой spans. `#line` помогает файлу и строке диагностики, но не заменяет полную карту синтетических выражений. ([GCC: Line Control](https://gcc.gnu.org/onlinedocs/cpp/Line-Control.html).)

### Импорт заголовка не равен безопасному вызову

Чтобы строго проверять lac до codegen, фронтенд должен знать C-сигнатуры. Простое добавление `#include` откладывает проверку на C-компилятор и не даёт lac собственных типов. Предлагается libclang: он предоставляет декларации, типы и позиции через C API. Для первого драфта нужно объявить поддерживаемое подмножество: функции фиксированной арности, числовые типы, ограниченные структуры и opaque handles; varargs, function-like macros, сложные callbacks и bitfields диагностировать как неподдерживаемые. ([Clang: Libclang](https://clang.llvm.org/docs/LibClang.html).)

Ручные bindings могут ускорить промежуточный тест `puts`, но не закрывают требование автоматического импорта произвольного конкретного header. Собственный parser части C допустим для специально ограниченных файлов, но не должен обещать всю стандартную библиотеку. Header зависит от target, defines, include paths и транзитивных headers; GCC предоставляет способы извлекать такие зависимости. Декларация функции также не задаёт линковку библиотеки с её реализацией. ([GCC: Preprocessor Options](https://gcc.gnu.org/onlinedocs/gcc/Preprocessor-Options.html).)

Нужна отдельная таблица соответствия lac и C ABI. `i` можно понизить в `int64_t`, но импортированный C `int` нельзя автоматически считать этим типом. В MSVC `int` и `long` имеют 32 бита даже для 64-битного target; размер `wchar_t` тоже не является универсальным контрактом UTF-16 для всех toolchain. ([Microsoft: Data Type Ranges](https://learn.microsoft.com/en-us/cpp/cpp/data-type-ranges?view=msvc-170).)

Для pointer-параметра следует явно знать, заимствует ли C буфер только до возврата, сохраняет ли его, меняет ли содержимое, кто освобождает результат. Managed reference и raw C pointer — разные типы. Сохранённый C-адрес требует registered handle/корня; nonmoving GC решает перемещение, но не достижимость. Callback с захватом требует context pointer или специальной обвязки и контракта времени жизни. Nullable C-результат проверяется на границе и преобразуется в отсутствие или ошибку lac. Заголовок не кодирует все эти обязательства; статья о blame полезна как концепция границы компонентов, но не доказывает безопасность произвольного C. ([Wadler и Findler, ESOP 2009](https://homepages.inf.ed.ac.uk/wadler/papers/blame/blame-tr.pdf).)

UTF-16 `s` нельзя cast-ом превратить в `char*`. Нужен адаптер в кодировку API, длину/NUL-терминацию и правило встроенного NUL. `c` предлагается определить как 16-битную кодовую единицу. Тогда `A` содержит одну единицу, `😀` — две, а `e` с combining acute — две кодовые точки, обычно одну grapheme. Unicode различает эти уровни; UAX #29 задаёт границы grapheme. Имутабельная строка из mutable buffer должна копировать его либо забирать владение, исключая дальнейшую мутацию. ([Unicode 16, глава 3](https://www.unicode.org/versions/Unicode16.0.0/core-spec/chapter-3/); [UAX #29, revision 49](https://www.unicode.org/reports/tr29/tr29-49.html).)

Переход на UTF-8 можно исследовать позднее для системных byte interfaces, но он меняет принятое решение и не гарантирует ускорение. До regex нужно определить единицу позиции совпадения и обработку malformed input. Для путей полезен самостоятельный Path-контракт; универсальная строка не должна молча обещать все особенности файловых API.

### CLI и кэш требуют отдельной спецификации

Исходник с `|` и `>>` внешняя shell может обработать раньше lac. Рекомендуемые, не утверждённые формы — `lac run file.lac`, `lac build file.lac -o app`, `lac eval 'source'`, `lac emit-c file.lac`. Утверждённый `>>` можно сохранить внутри исходника; нельзя обещать одинаковую некавыченную строку во всех оболочках. Для приложения и компилятора нужны отдельные argv.

В первом драфте драйвер вызывает toolchain с отдельными аргументами и записывает результат в заданный файл либо `a.exe`. Ошибка lac не запускает C-компилятор; ошибочная сборка не должна выдавать старый executable за свежий результат. Автоматический запуск и уникальная временная папка относятся к будущему temp-run P2; при его реализации запуск разрешается только после успешной сборки. Windows требует внимательной передачи имени executable и command line; это отдельный платформенный слой. ([Rust: Command](https://doc.rust-lang.org/std/process/struct.Command.html); [Microsoft: CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw).)

Кэш хранит бинарник, а каждый запуск выполняет его заново. Ключ включает исходники, версию/options lac, runtime, target/ABI, C toolchain/version/flags, транзитивные headers и параметры препроцессирования, линковку и связанные библиотеки. Только hash текста недостаточен. Запись должна быть атомарной, параллельные сборки — изолированными. Полностью воспроизводимая сборка может быть отдельным следующим проектом, а не условием первой функции сложения.

## 5. Развитие лучше проверять исполняемыми рубежами

### Последовательность работ без вымышленных сроков

Сначала нужен корпус грамматических и семантических примеров: для каждой программы задать AST/тип результата, stdout, exit code, побочные действия и ожидаемую ошибку. Затем реализовать числа, bool, объявления, блоки, статические функции и ветвления с C emission. Следующая внутренняя веха — импорт собственного header, `puts` с явным строковым адаптером и отдельная C-библиотека с линковкой. После этого — структуры, managed-конструкторы и GC, массивы, замыкания, range-iterator и `.collect`. Редактор использует те же позиции и токены, но терпит незавершённый ввод и восстанавливает разбор.

Эта последовательность не исключает уже обсуждавшиеся лямбды и sequence из полного драфта: она делит реализацию на проверяемые подэтапы. Только арифметический прототип нельзя объявлять всем первым драфтом. Сборка из файла и CLI, корректный import, память и согласованный набор синтаксиса должны работать вместе на обеих ОС.

| Приёмочная программа | Успешный сценарий | Отрицательный сценарий/проверка |
|---|---|---|
| `sum(a:i,b:i):i{a+b}` | Одинаковый результат на Linux/Windows и разных уровнях оптимизации | Wrong arity/type, согласованное переполнение |
| Условие и side-effect функции | Вычисляется одна ветвь; аргументы идут в заданном порядке | Число напрямую в bool-condition отклоняется по выбранному правилу |
| Корпус строк | Точный разбор закрытой/короткой формы, escapes и пустой строки | EOF, соседний вызов, незакрытая интерполяция дают локальную диагностику |
| Структура и копия | `p=point`, `P=Point`; `.cp` сохраняет вложенные ссылки | `p=Point` отклоняется; escape локального адреса невозможен |
| Возвращаемое замыкание | Окружение живёт после возврата функции | Запрещённый захват стекового адреса не проходит |
| GC-граф | Цикл без корней освобождается при сборке | Живой объект в nested value/FFI handle сохраняется |
| Sequence из трёх элементов | Три Item, затем End; fallback только на отсутствие | Failed read не превращается в End; повторный next следует контракту |
| `.collect` и раннее прекращение | Явный контейнер, порядок элементов, закрытие источника | Ошибка и `take` вызывают cleanup; бесконечный источник не материализуется без ограничения |
| C-import | Header, ABI, Unicode adapter и linked symbol работают | Missing header, unresolved symbol, nullable result, unsupported API различаются |
| CLI/output | Файл и quoted source эквивалентны; заданный output и default `a.exe` работают | Нет toolchain или сборка неуспешна — сообщается ошибка, старый файл не выдаётся за новую сборку |

После первого драфта следует двигаться к назначению языка: файловые API, byte input/output, процессы и типизированные конвейеры. Внутренний lac-этап может передавать объекты в одном процессе, внешний процесс — байты через ОС. Nushell служит практическим примером различения этих границ, без доказательства оптимальности для lac. ([Nushell: Pipelines](https://www.nushell.sh/book/pipelines.html).)

Раздельная компиляция модулей, отдельные объектные файлы и отдельные процессы — три разных решения. Object file требует линковки или загрузки, а процесс требует IPC-формата, статуса и cleanup. Предложение — сначала один executable для внутренних этапов и реальные процессы только для внешних утилит. Потом определить backpressure, отмену, `stderr`, раннее завершение потребителя и статус всего pipe. `grep` остаётся установленной системной утилитой, не встроенным в бинарник компонентом.

### Какие решения дадут наибольший выигрыш сейчас

Для начала реализации достаточно согласовать пять пакетов: режим сокращённых строк и разделители выражений; value/reference и исключение функциональных значений из правила регистра; checked arithmetic, преобразования и порядок вычислений; GC с корнями и различение Item/End/Error; границы автоматического C-import и явный файловый entry point. Подробности regex, полный editor UI и распределение будущих pipe-этапов могут подождать. Temp-run и кэш уже перенесены пользователем в низкий приоритет, их не требуется заново согласовывать для MVP. Остальные пакеты предлагаются на утверждение, а не объявляются новой спецификацией.

lac получит устойчивую индивидуальность через краткие записи поверх ясных контрактов. Для файлового языка особенно ценны предсказуемые ошибки, ленивое потребление и явные границы с системой; число сэкономленных знаков само по себе не доказывает удобство. Проверяемые эталонные программы позволят выбирать сахар по фактической читаемости и поведению, прежде чем дорогая реализация закрепит неоднозначности.

**Это анализ требований, а не benchmark и не формальная верификация lac.** Не построен компилятор, не измерены паузы GC, расход памяти, скорость сборки, удобство короткой грамматики или переносимость всех сторонних headers. Нет оснований обещать производительность Perceus, безопасность RustBelt или корректность CompCert для будущего lac. Рекомендации ранжированы по соответствию выбранным требованиям и сложности первого прототипа; их техническая состоятельность должна подтверждаться перечисленными программами и проверками.
