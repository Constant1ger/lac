# Память проекта lac

Обновлено: 2026-10-01. Это локальная память проекта, сохраняемая в Git.

## Утверждённые пользователем направления

- lac — очень лаконичный язык работы с файлами и системными утилитами, расширение или переработка Bash с возможностями языка высокого уровня вроде Kotlin.
- Строгая типизация. Первый драфт для Linux и Windows генерирует C только для кода lac; внешние команды и pipe не входят. Разрешены функции C через импорт заголовков `import *.h`, включая стандартную библиотеку; позже появятся алиасы lac. Без `>>` — компиляция во временную папку и запуск, `>> имя` — сохранение сборки. C toolchain пока не выбран. Кэш бинарников по хэшу рассматривается, но не обязателен.
- Типы: знаковые `i32/i64` или `i`, беззнаковые `u32/u64` или `u`, `f/d`, `c`, `b`. Типы указателей — с большой буквы.
- Примитивные типы по определению хранятся по значению, в том числе в коллекциях, без обязательного boxing или отдельного подсчёта ссылок. Явные указатели на примитивы — отдельные типы.
- Имена переменных без цифр, camelCase или snake_case.
- Создание всегда включает инициализацию; присваиваемого `null` нет.
- `{}` — scope, `[]` — массивы, `? A : B` — возвращающее значение ветвление с bool-условием. Дополнительно нужны `if/else` как в C; логические `and`, `or`, `xor`, `||`, `&&`, `!`.
- Функции как значения, анонимные лямбды, анонимные структуры, функции в структурах; методы — сахар, по умолчанию функции статические.
- Функция: `sum(a:i,b:i):i{a+b}`; лямбда: `():i{a+b}`. `:i` возвращает значение; последнее выражение в примере — результат. `i(a+b)` — значение на стеке, `I(a+b)` — объект в куче. Захват имён в лямбде и ранний возврат ещё нужно определить.
- Доступ через точку. Объект предложен как массив объектов с индексным доступом; смысл ещё нужно уточнить.
- Диапазоны `1..9`, `a..z`; pipe `|` для функционального стиля и работы с утилитами.
- `(a1..9){arr[a]+1}` возвращает результаты лямбды для индексов 1–9. `arr(1..9).+1` применяет `sum(value, 1)` к тем же элементам и возвращает результаты.
- `s` — строковый тип, строки иммутабельны. `c` использует UTF-16, размер строки соответствует числу элементов массива символов; точное подтверждение кодовых единиц против Unicode-символов ещё нужно. Мутабельный массив символов преобразуется в строку через `S()` или `.toS`. Интерполяция `$val` и `$val.lenght`, включая значения и методы. Нужны регулярные выражения.
- Строка открывается двойной кавычкой; без закрывающей её завершают неэкранированные `)`, `}`, `]`, `,`. Символы можно включать в текст явным закрытием или экранированием (последнее уточняет прежний запрет). Экранируются также `$`, кавычка и обратная косая черта. Пустая строка — `""`; `f("a","b")` равно `f("a,"b)`. Алгоритм однозначного разбора ещё не выбран.
- `db_item{...}` описывает структуру. Поле `type="warn` имеет значение по умолчанию и выведенный строковый тип. `db_item(...)` вызывает конструктор; пользователь также допускает совмещение конструктора с определением структуры.
- Точка входа — первая функция, включая анонимную `(s){...}` с типом строки без имени параметра. `(s)` получает весь вывод программы лениво. Можно задать вход явно как `main()` или `m()`. Компиляция из файла или командной строки.
- Range — фиксированные границы; Sequence — ленивое вычисление. Есть только оператор `..`; `0...size` — это `0..` и `.size`. `{0..5}` — heap-лямбда, задающая sequence; `seq={0..5}` создаёт именованный счётчик, `.next` сохраняет состояние. Все лямбды в куче. Границы и завершение не определены.
- `.` — краткое `it`, элемент коллекции/потока либо анонимный аргумент в scope функции. `[..]` — forEach по всему массиву. `.{func(.)}` обходит sequence/массив или применяется к анонимной переменной.
- `.collect` равнозначно `.collect()`, потребляет sequence/stream до завершения, собирает результат и закрывает источник; может приводить к коллекции. Целевой контейнер и результат по умолчанию ещё не выбраны. Методы без аргументов можно вызывать без скобок.
- Конструкция `array.{body}` обходит каждое значение массива; после `.collect` блок выполняется поэлементно.
- `>> script.exe` сохраняет скомпилированный сценарий с вызовом `grep`; без имени — `a.exe` или `a.out`. Утилиты вызываются из системы, не упаковываются; без установленного grep сценарий не работает. Внешние команды отложены. Возможные отдельные объектные файлы этапов pipe — предложение, не решение.
- Запуск `lac` без аргументов открывает редактор с подсветкой определений переменных, функций, структур и других конструкций.
- Первоначально память планировалась через RC. Последнее желание — Java-подобная достижимость: нет пути из активных корней через граф объектов — объект подлежит удалению. RC сам по себе не собирает недостижимые циклы; алгоритм GC/обнаружения циклов ещё не выбран. Ссылок на стековые объекты нет; автоматический перенос в кучу при попытке создать ссылку рассматривается, но не принят. Borrow checker пока не требуется.
- Последнее уточнение размещения: `db_item(...)` создаёт объект на стеке, `Db_item(...)` — в куче; описание остаётся `db_item{...}`. Это меняет ранее предложенную связь большой буквы со стеком. Пользователь предложил в эталонном примере использовать `.Db_item(...)` из-за объёма данных. Оба варианта синтаксически допустимы; неподходящий выбор размещения — ошибка программиста.
- Последнее правило структур: `p=point(...)` — прямое значение на стеке; `P=Point(...)` — указатель P на стеке, объект в куче; `p=Point(...)` — ошибка компиляции. Прежний `P=point(...)` не считать согласованным примером. `seq={}` разрешено как указатель на функцию с маленьким именем. Объявления примитивов `a:d=3`, `a=5.55`, `A=3` сохраняются; формализация указателей-примитивов ещё нужна.
- `i32/u32/f` — 32 бита, `i/u/d` — 64 бита. Типа `y` нет: это был русский предлог «у». Импорт любого конкретного `.h`, не wildcard. Автоматические числовые преобразования как в C, явные через конструктор типа. `d:b=1` — допустимая инициализация, но условие требует bool.
- Массивы хранят сами значения/объекты непосредственно; коллекции `Array`, `Map` и другие хранят ссылки на объекты, а примитивы — по значению. `Array` в lac — коллекция, отличная от обычного массива. Это собственная модель lac, не точная копия Kotlin/JVM.
- Присваивание ссылок копирует адрес в куче. `Pnt=Point(p)` — копия объекта в куче; прежний `pnt=Point(p)` запрещён последним правилом. `.cp` — копия, `.dpcp` — глубокая копия; типы/размещение результатов методов и копии графов ещё нужно определить.
- `Map` и коллекции не содержат null. `getIfPresentOr` принимает лямбду, вызываемую при отсутствии значения; полная сигнатура не задана. `(try)? :` как аналог try/catch — предложение, не решение.
- Необработанную ошибку пользователь предложил завершать как `Segmentation fault`; реализация исключений и кроссплатформенное поведение не определены. Для sequence нужен безопасный метод и предложена форма `=seq.next?{/*what to do if exp*/}`. Значение обработчика и различие с тернарным `? :` ещё не выбраны.
- Требуется определить размещение буфера `.collect`, поведение при сборе sequence указателей, целевой контейнер и время жизни значений. Не утверждать, что стековые временные объекты обязательно накапливаются: перенос значения и переиспользование слота могут менять поведение.

## Не выдавать предложения за решения

Не утверждены: язык реализации компилятора, точные правила проверки типов, совместимость с Bash, ленивость преобразований массивов, нулевая индексация, точная единица длины UTF-16, `${...}`, `length`, немедленное освобождение, алгоритм GC, слабые ссылки, `Option<T>`, однопоточная модель и изменяемость объектов. C-бэкенд, UTF-16, иммутабельные строки и размеры `i/u/f/d` уже выбраны.

Открытые вопросы: разбор строк, EOF, sequence внутри обхода и исчерпание, вложенная точка, область определения структур, точка входа, FFI-сигнатуры и C-указатели, GC и копии графов, исключения, интерфейс редактора. Упаковка утилит не требуется. `..`/`...`, `[..]`, отсутствие типа `y`, смысл импорта и базовая сигнатура функции уже уточнены.

Предложение для парсера: завершающая скобка или запятая не входит в значение строки и остаётся частью окружающей конструкции. Это детализация ассистента, отдельно не утверждённая пользователем.

## Порядок дальнейшей работы

Продолжать обсуждение конкретными короткими программами и уточнять семантику до реализации. Сохранять краткость синтаксиса как основную цель. При изменении решений обновлять эту память и соответствующий раздел спецификации.

Коммиты делать только по явному указанию пользователя. Документацию и память можно обновлять без коммита.
