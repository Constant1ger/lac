# Предварительная спецификация lac

Статус: проектирование, 2026-10-01. Ниже требования пользователя отделены от предложений и открытых вопросов. Примеры иллюстрируют обсуждавшиеся конструкции, а не готовую грамматику.

## Назначение

lac должен стать расширением или полной переработкой Bash: очень лаконичным языком работы с файлами и системными утилитами, поддерживающим возможности современного языка высокого уровня вроде Kotlin.

Требуется строгая типизация. Первый драфт предназначен для Linux и Windows и компилирует код lac в C. Внешние утилиты вроде `grep` в первый драфт не входят. Поддерживается явный импорт C-заголовков для вызова функций C, включая стандартную библиотеку; позднее планируются алиасы lac без явного импорта. Предусмотрены однократное выполнение и компиляция через `>>`; детали запуска C-компилятора пока не выбраны. Совместимость с существующими Bash-скриптами не определена.

Запись `import *.h` обозначала возможность импортировать любой конкретный заголовочный файл `.h`, а не требование wildcard-импорта. Остаются открытыми точный синтаксис путей, получение сигнатур и типы на границе C/lac.

## Требования пользователя

### Типы

| Обозначение | Назначение |
| --- | --- |
| `i32`, `i64` или сокращение `i` | Знаковые целые |
| `u32`, `u64` или сокращение `u` | Беззнаковые целые |
| `f`, `d` | Числа с плавающей точкой |
| `c` | Символ |
| `b` | Логический тип |
| `s` | Строка; в примере также обозначает тип без имени параметра |

Типы указателей обозначаются названиями типов с большой буквы. Последнее уточнение пользователя для конструкторов: `db_item(...)` создаёт объект на стеке, `Db_item(...)` — в куче. Это уточнение меняет ранее предложенное направление правила, связывавшего большую букву со стеком. Связь типов указателей, конструкторов, подсчёта ссылок и времени жизни ещё требует формального определения.

По последнему уточнению: `u32`, `i32`, `f` имеют 32 бита; `d`, `i`, `u` — 64 бита. Типа `y` нет: пользователь имел в виду русский предлог «у». Автоматические числовые преобразования — как в C; явное преобразование задаётся конструктором типа `i(value)`/`d(value)` для стекового значения либо `I(value)` для значения в куче. Переполнение и типы литералов требуют детализации.

Примитивные типы `i32`, `i64`, `i`, `u32`, `u64`, `u`, `f`, `d`, `c`, `b` хранятся по значению по определению, в том числе в массивах и коллекциях. Для них не требуется неявное создание отдельного объекта с подсчётом ссылок. Явный указатель на примитив — отдельный тип; правило хранения примитива по значению не отменяет поддержку таких указателей.

По последнему уточнению, `c` использует UTF-16. Рабочее прочтение — одна 16-битная кодовая единица; оно требует окончательного подтверждения для символов вне BMP.

### Имена и создание переменных

- Имена переменных не содержат цифр; используются camelCase или snake_case.
- Точный набор допустимых букв и символов предстоит определить.
- Ограничение цифр относится к именам переменных; обозначения типов `i32` и `u64` сохраняются.
- Создание переменной всегда включает инициализацию.
- `null` для присваивания переменным отсутствует.
- Явный тип задаётся как `имя:тип=значение`, без типа используется вывод типа.
- Для структур согласованные формы: `p=point(...)` — прямое стековое значение; `P=Point(...)` — переменная-указатель на стеке, объект в куче. `p=Point(...)` — ошибка компиляции. Смешанная форма `P=point(...)` больше не является согласованным примером; её допустимость нужно определить отдельно.
- `seq={}` явно разрешено как указатель на функцию, несмотря на маленькую букву имени. Грамматика и типы функциональных значений должны учитывать эту форму.

Примеры пользователя:

```plaintext
a:d=3 b:u=3 c:s="text", d:b=1
a=5.55 b=3f c="test"
A=3 B=5.5 C=true
p=point(x=4.4,y=5.1)
P=point(4.4,5.1)
Point(1f,6.2)
```

`p=point(x=4.4,y=5.1)` одновременно описывает структуру с полями `x`, `y` и вызывает конструктор на стеке. Позднейшее уточнение исправляет heap-пример на `P=Point(4.4,5.1)`: сам указатель находится на стеке, объект — в куче. `Point(1f,6.2)` — анонимный объект в куче. Исходная строка `P=point(...)` выше сохранена как история обсуждения. Сопоставление дробных типов полей должно следовать выбранным правилам преобразований.

`d:b=1` допустимо как явно приведённый к `b` инициализатор согласно пользовательскому примеру; это не разрешает использовать число напрямую как условие. Разделители соседних объявлений, повторное присваивание и неизменяемость ещё требуют определения.

### Блоки и ветвления

Области видимости задаются фигурными скобками `{}`.

Поддерживается выражение:

```plaintext
значение_или_функция ? A : B
```

Ветвление может возвращать значение. Условие принимает только `b`. Дополнительно поддерживаются `if` и `else` с поведением как в C; это уточняет прежнее предложение использовать только тернарную форму. Логические операции: `and`, `or`, `xor`, `||`, `&&`, отрицание `!`. Точные приоритеты, соответствие словесных и символьных форм, короткое замыкание и совместимость типов ветвей ещё требуют формального определения.

### Массивы, диапазоны и преобразования

Массивы используют квадратные скобки. Обсуждавшаяся запись создания и присваивания:

```plaintext
=[1,2,3]
```

По последнему решению пользователя, массивы хранят сами значения/объекты непосредственно в своих элементах, а коллекции `Array`, `Map` и другие хранят ссылки на объекты. Примитивы по определению хранятся по значению, включая коллекции. Название `Array` здесь относится к коллекции lac, отличной от обычного массива.

Это правило о представлении элементов, а не о размещении всего контейнера: буфер массива может находиться на стеке или в куче. Представление вложенных полей объектов также определяется их типами; непосредственное хранение объекта не означает глубокого копирования всех его данных.

Предложение для интеграции с подсчётом ссылок: ссылки в коллекциях являются владеющими; вставка и удаление должны соответствующим образом учитывать владение. Точный синтаксис типов контейнеров, правила копирования/перемещения и хранения ключей `Map` ещё не определены. Примитивные элементы хранятся непосредственно, без обязательного boxing.

Присваивание ссылки копирует адрес heap-объекта, а не сам объект. Явная копия создаётся через `Point(p)` или универсальный метод `.cp`, глубокая — `.dpcp`. Ранний пример `pnt=Point(p)` заменён позднейшим правилом: маленькое имя с большим конструктором запрещено; согласованная форма — `Pnt=Point(p)`. Размещение результатов `.cp`/`.dpcp`, их типы и поведение для вложенных полей, циклов и общих дочерних объектов ещё требуют определения.

`Map` и другие коллекции не содержат `null`. Пока отсутствие значения обрабатывается методом `getIfPresentOr`, которому передаётся лямбда, вызываемая только при отсутствии значения. Полная сигнатура, тип возвращаемого значения и правило сохранения значения по умолчанию в коллекцию не определены. Форма `(try)? :` обсуждается как возможный аналог try/catch, но не принята.

Сравнение с Kotlin — ориентир, не точное совпадение: Kotlin/JVM различает массивы примитивов без boxing и обычный `Array<T>` объектов; `Array` в Kotlin не относится к коллекциям. Для lac принято собственное различие между массивом значений и ссылочной коллекцией. См. [массивы Kotlin](https://kotlinlang.org/docs/arrays.html) и [коллекции Kotlin](https://kotlinlang.org/docs/collections-overview.html).

Диапазоны: `1..9`, для символов — `a..z`. Требуется функциональность диапазонов, аналогичная Kotlin. Синтаксис символьных литералов, шаг, обратный обход и правила границ предстоит определить.

Обсуждавшиеся записи обхода:

```plaintext
(1..9){}
(a1..9){arr[a]+1}
arr(1..9).+1
```

Уточнение пользователя:

- `(a1..9){arr[a]+1}` вызывает лямбду в `{}` для индексов от 1 до 9 и возвращает соответствующие значения `arr` плюс 1.
- `arr(1..9).+1` возвращает значения элементов с индексами от 1 до 9, применяя к каждому `sum(value, 1)`.
- Эти примеры описывают возвращаемые результаты, а не присваивание новых значений элементам исходного массива.
- В сокращённой форме точка обозначает текущий элемент (`it`).

По последнему уточнению пользователя, есть только оператор диапазона `..`. Три точки в `0...size` — это `0..` и обращение к текущему элементу `.size`, а не самостоятельный оператор `...`.

`Range` представляет фиксированные границы от/до. `Sequence` представляет ленивое поэтапное вычисление. Пользователь ориентируется на Kotlin, но точные правила границ, шага и завершения должны быть явно определены в lac.

```plaintext
{0..5}
seq={0..5}
seq.next
```

`{0..5}` — анонимная лямбда в куче, задающая sequence. Все лямбды размещаются в куче. `seq={0..5}` задаёт именованный счётчик; каждый `.next` возвращает следующее значение с сохранением состояния. Размещение самой лямбды не отменяет необходимости определить время жизни переменной, содержащей ссылку на неё.

Точка `.` — краткая запись `it`: текущий элемент коллекции/стрима либо анонимный аргумент функции внутри её scope. Разрешение вложенных контекстов ещё не определено. `[..]` означает forEach по всему массиву. Ленивость преобразования массива, включение верхней границы, начальный индекс, результат после исчерпания и выход за границы также требуют уточнения.

`.collect` эквивалентно `.collect()`: потребляет sequence/stream до завершения, собирает результат и закрывает источник. По последнему уточнению пользователя, может приводить поток к коллекции; ранее обсуждался результат-массив. Выбор целевого контейнера, результат вызова без указания контейнера, повторное использование и поведение при ошибке ещё не определены.

Если sequence выдаёт умные указатели, нужно определить правила сбора в массив значений либо ссылочную коллекцию; не подразумевать неявную глубокую копию.

Конструкция `.{func(.)}` выполняет лямбду для всех элементов sequence или массива; она также может применяться к анонимной переменной. Это поэлементный обход, в том числе после `.collect`. Возвращаемое значение этой конструкции ещё не определено.

### Структуры и функции

Синтаксис функции и сокращённой лямбды:

```plaintext
sum(a:i,b:i):i{a+b}
():i{a+b}
i(a+b)
I(a+b)
```

`:i` явно задаёт возвращаемый тип значения; пользователь описывает его как результат на стеке. Последнее выражение `a+b` в приведённой функции является результатом. `():i{a+b}` — лямбда без объявленных параметров; имена `a`, `b` должны разрешаться в доступном окружении, точные правила захвата ещё не определены. `i(a+b)` создаёт целочисленное значение, `I(a+b)` — целочисленный объект в куче. Синтаксис возвращаемого указателя, раннего возврата и нескольких выражений блока ещё требует определения; возвращение ссылки на локальный стековый слот не подразумевается.

- Поддерживаются структуры данных, в том числе анонимные и без имени переменной.
- Функции являются объектами/значениями, включая анонимные лямбды.
- Структуры могут содержать объекты функций.
- Методы описаны пользователем как синтаксический сахар; по умолчанию функции статические.
- Доступ к переменным/полям и методам объекта осуществляется через точку.
- Пользователь предложил: «объект — массив объектов, к нему можно обращаться как к массиву». Типизация и точная семантика такого доступа пока не определены.

Описание структуры использует фигурные скобки, вызов конструктора — круглые:

```plaintext
db_item{id:i,text:s,type="warn}
db_item([0...size].next,.)
```

`type="warn` задаёт значение поля по умолчанию с автоматически выведенным строковым типом. Конструктор может не передавать это поле.

Размещение задаётся регистром первой буквы конструктора:

```plaintext
db_item([0...size].next,.)
Db_item([0...size].next,.)
```

Первая запись — стековое размещение, вторая — размещение в куче. Описание структуры остаётся `db_item{...}`. Оба вызова синтаксически допустимы. Пользователь предложил использовать в эталонном сценарии второй вызов, чтобы избежать риска переполнения стека при большом объёме данных; неверный выбор размещения рассматривается как ошибка программиста, а не синтаксиса.

По уточнению пользователя, запись `db_item([0...size].next,.,"warn)` также может совмещать вызов конструктора с определением структуры. Правила вывода имён полей и регистрации такой структуры пока не определены.

Методы без аргументов можно вызывать без круглых скобок: `.collect` и `.collect()` эквивалентны. Нужно определить различие между таким вызовом и получением функции как значения.

Точка входа — первая функция, в том числе анонимная. В примере это `(s){...}`, где задан тип строки без имени параметра. По уточнению пользователя, `(s)` получает весь вывод программы лениво. Представление такого ленивого строкового входа и момент материализации ещё требуют определения. Входную функцию можно задать явно как `main()` или `m()`. Программа компилируется из файла либо напрямую из командной строки. Правила приоритета явной точки входа и передачи исходника через оболочку ещё требуют определения.

Нужно различить методы с получателем и поля, хранящие функции с захваченным окружением. Базовая форма объявления функции уже задана; грамматика захватов и анонимных структур ещё требует детализации.

### Ошибки и исчерпание sequence

Пользователь предложил аварийное завершение необработанной ошибки как `Segmentation fault`. Это желаемое поведение для обсуждаемого прототипа; способ генерации сигнала/завершения на Linux и Windows и область применения ещё не определены. Механизм исключений нужно спроектировать отдельно, не считать его реализованным.

Нужны безопасный метод по аналогии с `getIfPresentOr` и форма перехвата:

```plaintext
=seq.next?{/*what to do if exp*/}
```

Форма сохранена как предложена пользователем. Нужно определить, запускает ли блок только обработку ошибки, возвращает ли запасное значение, как передаётся ошибка, что возвращается при успехе и как эта форма отличается от тернарного `? A : B`. Включение верхней границы range остаётся открытым.

### Строки

Строки обязательно открываются двойной кавычкой. Закрывающую кавычку можно опустить: тогда строку закрывает любой из неэкранированных символов `)`, `}`, `]`, `,`. Для включения этих символов в текст можно явно закрыть строку кавычкой или экранировать символ. Это дополняет прежнее правило об обязательной закрывающей кавычке. В явно закрытой строке эти символы внутри текста не завершают строку. Пользователь определяет строки как массивы `char`, с которыми можно работать как с массивами.

Предлагаемая детализация для парсера: завершающая скобка или запятая не входит в строку и остаётся токеном окружающей конструкции. Примеры применения правила:

```plaintext
print("hello)
db_item{type="warn}
["hello]
STD.Db("localhost:5432,"login:psw)
```

Примеры строк, содержащих закрывающие скобки или запятую, с обязательной закрывающей кавычкой:

```plaintext
print("hello)world")
print("items[done]")
print("value}")
print("hello, world")
```

Экранируются скобки, `$`, двойная кавычка, запятая и сама обратная косая черта. Пустая строка — `""`. `f("a","b")` и `f("a,"b)` равнозначны. Пользователь также указал эквивалентность закрытой строки `f("a,b")` и сокращённой записи с экранированной запятой. Точное отображение пар обратных косых черт в исходном сообщении нужно отличать от реальных символов исходника lac; таблица escape-последовательностей ещё не оформлена.

Остаются открытыми EOF и алгоритм однозначного различения явно закрытых и сокращённых литералов, особенно нескольких соседних строк. Утверждение допустимости строк ещё не задаёт алгоритм лексического разбора.

Незакрытые двойные кавычки в эталонном примере намеренны; нельзя автоматически считать их опечатками. Символьный литерал `'\n'` присутствует в примере, но его общая грамматика отдельно не определена.

Поддерживается интерполяция значений и доступ к внутренним значениям и методам:

```plaintext
"текст $val текст"
"text $val.lenght text"
```

`lenght` сохранено как в пользовательском примере; окончательное имя встроенного свойства не утверждено.

Обсуждались, но не утверждены: `${expression}` для произвольного выражения, запись вызова `$val.method()`, имя свойства `length`, правила преобразования значений в текст. Возможность экранировать `$` уже утверждена.

Строки иммутабельны и используют UTF-16. Размер определяется числом элементов массива символов. Массив символов может быть мутабельным; преобразование в строку — `S()` или `.toS`. Точная сигнатура `S()`, копирование/перенос буфера и защита от последующей мутации исходного массива ещё требуют определения.

Для формализации предлагается считать размер числом кодовых единиц UTF-16, а не видимых символов: например, emoji вне BMP занимает два элемента. Это рабочая детализация ассистента, пока не отдельное решение пользователя. См. [Char в Kotlin](https://kotlinlang.org/docs/characters.html) и [длина CharSequence](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/-char-sequence/length.html).

Стоимость индексного доступа и регулярные выражения требуют дальнейшей спецификации. Нужны явные преобразования UTF-16 lac в кодировку C API и внешних потоков.

### Pipe, файлы и программы

Оператор `|` поддерживает функциональный стиль, аналогичный по назначению Bash-конвейерам, с возможностями преобразования данных уровня Kotlin.

Требуется работа с системными утилитами, включая `grep`, `cat`, `tail`.

Это долгосрочное требование; первый драфт компилирует только lac-код в C и поддерживает явно импортированные функции C. Запуск и упаковка внешних команд не входят в первый драфт.

Pipe пока не реализуется. Пользователь рассматривает вариант отдельных объектных файлов и раздельной компиляции/исполнения этапов lac, но архитектура не выбрана. Сам объектный файл не является самостоятельной запускаемой программой; способ линковки и границы процессов остаются открытыми.

Открыты: синтаксис запуска, поиск исполняемых файлов, аргументы, окружение, рабочая директория, перенаправления, потоки `stdin/stdout/stderr`, статусы, отмена и обработка ошибок.

Предложения для обсуждения:

- Отличать типизированные последовательности от потоков байтов внешних процессов.
- Передавать аргументы отдельными значениями, без неявного исполнения строки через Bash.
- Обеспечить потоковую обработку без обязательной загрузки всего вывода в память.
- Явно описать преобразование байтов в строки и типизированные значения.

### Режимы запуска и сборки

- Без `>>` программа выполняется один раз.
- Однократный запуск обязательно компилирует программу во временную папку и затем запускает собранный результат; интерпретатор в этом режиме пока не предусматривается.
- `>> script.exe` компилирует весь сценарий исполнения в исполняемый файл, включая этап с `grep`.
- Если после `>>` имя не задано, результат сохраняется как `a.exe` или `a.out`; правило выбора имени и платформы нужно определить.
- `>>` здесь означает сборку, а не дописывание стандартного вывода в файл.

Внешний `grep` вызывается из системы: без установленной утилиты сценарий не выполняется. Утилита не включается в исполняемый файл. Требование «вместе с grep» означает сохранение сценария вызовов, а не упаковку бинарника утилиты. Работа с внешними утилитами остаётся последующей стадией.

Возможный будущий кэш: искать собранную программу во временной папке по хэшу кода. Это предложение пользователя, а не обязательная часть первого драфта. Предложение для корректного ключа: учитывать также версию компилятора lac, целевую платформу, параметры сборки и зависимости импортированных заголовков. Повторный запуск кэшированного бинарника всё равно должен заново исполнять программу; не кэшировать её побочные действия или вывод вместо исполнения.

Политика очистки временных файлов, передача исходника через оболочку и требования к установленному C toolchain пока не определены.

### Редактор и подсветка

Запуск `lac` без аргументов открывает редактор кода. Требуется подсветка определений переменных, функций, структур данных и других конструкций языка.

Тип интерфейса редактора пока не выбран. Подсветка должна учитывать контекстные границы строк, описания структур и функции без имён параметров. Обсуждаемое предложение: использовать общий разбор исходника для редактора и исполнения, а разрешение имён — для семантической подсветки.

### Эталонный сценарий

Исходная пользовательская запись, без исправления необязательных закрывающих кавычек:

```plaintext
lac grep -Ei "warn|warning" app.log | db_item{id:i,text:s,type="warn} (s){.split('\n')[..].db_item([0...size].next,.).collect.{STD.Db("localhost:5432,"login:psw).save(.);STD.HttpCli("localhost:8089).post(STD.toJson(.))} >> script.exe
```

Сценарий задаёт поиск строк, описание структуры с полем по умолчанию, строковую входную функцию, разбиение вывода, преобразование строк в записи, сбор в массив и поэлементные действия сохранения и HTTP-отправки; `>>` задаёт сборку всего сценария.

Позднейшее уточнение размещения: пользователь предложил заменить вызов `.db_item([0...size].next,.)` на `.Db_item([0...size].next,.)`, чтобы создавать записи в куче. Исходная запись выше оставлена как история обсуждения; она не является синтаксической ошибкой.

В `STD.Db("localhost:5432,"login:psw)` запятая завершает первый строковый аргумент, а `)` — второй.

`[..]` уже определено как forEach; `0...size` состоит из `0..` и `.size`. Открытые вопросы примера: получатель `.size` внутри преобразования, создание счётчика один раз для последовательных `.next`, завершение sequence, драйвер БД, обработка ошибок и время жизни клиентов БД/HTTP. Формальная семантика точки в каждом вложенном контексте ещё не определена. Этот полный сценарий выходит за границы первого драфта.

### Начальная модель памяти

Первоначальная реализация обсуждалась как умные указатели с подсчётом владений. Последняя желаемая семантика пользователя — Java-подобная достижимость: объект удаляется, когда на него нет ссылок из активных корней или через граф живых объектов. Ссылки на стековые объекты в lac отсутствуют; перенос объекта в кучу при попытке получить такую ссылку предложен пользователем как возможный механизм, но не выбран окончательно.

Простой подсчёт ссылок не обеспечивает это правило для недостижимого цикла `A → B → A`: внутренние ссылки сохраняют ненулевые счётчики. Требуется выбрать tracing GC, подсчёт ссылок с обнаружением циклов либо ограниченную начальную модель. Конкретный алгоритм пока не выбран; не считать Java-подобную достижимость реализованной только за счёт счётчиков. В Java отсутствие пути от корней делает объект кандидатом на сборку, но не обещает немедленного удаления: [Oracle о достижимости](https://docs.oracle.com/en/java/javase/26/gctuning/other-considerations.html).

Предыдущий ориентир — быстрая и безопасная модель, похожая на Rust. Полноценная проверка заимствований не является требованием начальной реализации.

Детали, предложенные ассистентом, но ещё не утверждённые:

- Учитывать владеющие ссылки в переменных, структурах, массивах и замыканиях.
- Увеличивать счётчик при копировании указателя, уменьшать при его уничтожении или перезаписи; перемещение не увеличивает счётчик.
- Освобождать объект немедленно при нулевом счётчике вместо отложенного удаления.
- Предусмотреть слабые ссылки для разрыва циклов и специальный тип отсутствующего результата.
- Начать с однопоточного исполнения.

Необходимые решения: момент фактического удаления, циклы владения, совместное изменение, потокобезопасность, стековые объекты и захваты лямбд. Подсчёт ссылок сам по себе не решает эти вопросы.

Массивы хранят значения непосредственно; коллекции `Array`, `Map` и другие — ссылки на объекты, но примитивы в них хранятся по значению. Отдельно требуется определить размещение буфера массива, создаваемого `.collect`, и правила для последовательностей умных указателей. Создание временного объекта на стеке не обязательно накапливает все объекты на стеке: слот может переиспользоваться, а значение переноситься в буфер массива. Поэтому риск переполнения зависит от выбранной семантики хранения, размера объектов и реализации, а не только от числа итераций.

Подсчёт ссылок не продлевает физическое время жизни стекового объекта. По последнему требованию пользовательские ссылки на стек не существуют. При возможном переносе в кучу ещё нужно определить, сохраняется ли идентичность объекта, что происходит с исходным значением и его дальнейшими изменениями.
