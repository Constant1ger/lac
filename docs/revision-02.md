# Ревизия 2: строки, обход, операторы и память

Дата: 2026-10-01. Основана на последних прямых уточнениях пользователя. При противоречии с предыдущими примерами в `language.md`, `draft-01.md` или исследовательском отчёте эта ревизия имеет приоритет. Неперечисленные ранее принятые решения сохраняются. Выбрана модель единственного владельца, как в Rust; детали заимствований ещё проектируются.

## Строки и интерполяция

- Строка обязательно закрывается двойной кавычкой: `"text"`. Сокращённые строки отменены; запятая и скобки внутри строки больше не являются её завершителями.
- Строка — неизменяемая структура с неизменяемыми ASCII-данными. Это заменяет прежнее требование UTF-16 для обычных строк.
- Пользователь подтвердил представление `{data, size}`: данные без завершающего NUL и отдельный размер. Строка неизменяема целиком: нельзя изменять её данные или поля представления. Для ASCII размер в байтах совпадает с числом символов.
- В будущем рассматриваются `u8""`, `u16""`, `u32""`.
- Нужно рассмотреть `{expr}` без `$` для всех случаев интерполяции. Это пока предложение, не окончательная грамматика.
- Прежняя иммутабельность сохраняется; кодировка и ширина отдельного `c`, а также `S()`/`.toS` требуют согласования с новым представлением.

Предложение: внутри строки `"sum={a+b}"` вставляет форматированное значение. `$` тогда обычный символ. Для буквальных фигурных скобок выбрать `{{`/`}}` либо экранирование. Снаружи строки `{expr}` остаётся блоком/лямбдой согласно контексту и не вызывает форматирование само по себе. Под «для всех случаев» можно понимать поля, вызовы и составные выражения внутри интерполяции; распространение на весь язык ещё нужно обсудить.

Форматирование в ASCII должно иметь правило для не-ASCII данных, например запрет/ошибка или явное кодирование; молчаливая потеря символов не определена. Для C API, ожидающего NUL-terminated строку, требуется отдельный адаптер; передавать `data` как такую строку без преобразования нельзя.

## Неизменяемые коллекции

У всех коллекций должен быть неизменяемый аналог. Явно названы `iList`, `iSet`, `iArr`; точные имена остальных аналогов, включая Map, ещё нужно определить.

Неизменяемый контейнер не допускает добавления, удаления или замены элементов. Режим `fe`, записывающий результат callback в элемент, для него недоступен; обход с действием, например печатью, допустим. Ленивая трансформация создаёт новые элементы, сохраняя исходный контейнер.

Открыто: означает ли неизменяемость также запрет изменения полей объектов внутри контейнера через другие заимствования. Не приравнивать неизменяемость контейнера к глубокой неизменяемости всего графа автоматически. Также нужно определить преобразование mutable/immutable контейнеров и сохраняет ли `.collect` неизменяемое семейство источника; синтаксис `.iList`/`.iSet`/`.iArr` пока не утверждён.

## forEach и мутация

Прежняя форма `[..]` для обхода/мутации заменяется методом `fe` и trailing lambda.

Пользовательские формы:

```plaintext
array.fe(lambda = (x : ArrayElementType) { x = x + 1 } ))
array.fe{@(. + 1)}
array.fe{@(+1)}
array.fe{prln(.)}
array.fe{prln("a")}
```

Первая строка сохранена как исходный иллюстративный пример; точная грамматика именованного аргумента и баланс скобок ещё не нормализованы. Формы возврата обновлены по последнему решению: прежние `fe{+1}` и `fe{. + 1}` больше не возвращают новое значение без `@`.

- `f((){})` может сокращаться до `f{}` для функции с подходящим lambda-аргументом.
- Тип аргумента лямбды может выводиться из элемента контейнера; `.` обозначает текущий элемент.
- `+1` в таком контексте означает `sum(., 1)`, а не обычную самостоятельную константу с унарным плюсом.
- Для явно возвращаемого через `@` нового значения пользователь намерен менять соответствующий элемент. Без `@` callback не возвращает значения и выполняется только действие; результат последнего выражения не записывается в элемент.
- `array.fe{prln(.)}` печатает элементы; `array.fe{prln("a")}` печатает `a` столько раз, сколько элементов.

Требуется формализовать два режима callback: возвращает тип элемента для записи результата или не возвращает значения. Также нужно решить, является ли именованный `x` изменяемым доступом к элементу или локальной копией: присваивание локальному примитиву само по себе не меняет массив. Предложение для краткой формы — вычислить callback и записать возвращаемое значение в текущий слот; void/Unit-callback не выполняет неявную замену. Это не даёт пользователю сохраняемой ссылки на стековый слот.

Для `Set`/ключей `Map` и неизменяемых контейнеров мутацию нужно ограничить или определить отдельно; изменение значения, участвующего в хэше, не должно молча нарушать контейнер.

Явный `@` решает проблему случайного возврата результата `println()` или числового результата C-функции `printf`: без `@` результат вызова не становится результатом лямбды. `array.fe{println(.)}` выполняет печать; возврат и проверка типа результата происходят только при явно указанном `@`.

## Ленивая трансформация

```plaintext
array.(x : ArrayElementType){ @(x + 1) }
```

Эта конструкция возвращает sequence новых элементов и не меняет исходный контейнер. Пример обновлён: значение элемента возвращается явно через `@`; старая лямбда `{x+1}` без `@` ничего не возвращает. Можно собрать её:

- `.collect` — в тот же вид контейнера, что исходный, с подходящим типом результата;
- `.List`, `.Set`, `.arr` — соответственно в явно выбранный вид контейнера.

Конкретная политика для трансформации Map, изменения типа элемента, повторяющихся значений Set, владения исходным контейнером и конечного результата ещё не определена. «Тот же тип» пока трактуется как семейство контейнера, но это требует подтверждения, если lambda меняет тип элемента.

## Возврат и операторы

- Явный возврат в функциях и лямбдах: `@val`, вместо прежнего `>val`. Знак `>` больше не обозначает return.
- В лямбде без `@` значение не возвращается, даже если последнее выражение или вызов вычисляет значение. Неявный возврат последнего выражения в лямбдах отменён.
- Актуальные примеры: `sum(a:i,b:i):i{@(a+b)}` и `():i{@(a+b)}`. Скобки после `@` группируют выражение, отдельного оператора `@()` не вводится.
- Нужно определить возврат без значения, диагностику отсутствующего возврата при объявленном типе результата и все пути управления. Предложение: для функции/лямбды с типом результата требовать `@` на каждом нормально завершающемся пути; обычный блок сам по себе не получает семантику return.
- Сравнение `>` или `<` разных типов — ошибка компиляции, несмотря на C-подобные преобразования в арифметике.
- `#` сравнивает адреса ссылок. Сравнение указателей на разные типы структур — ошибка компиляции.
- Прямой `#` двух `f` или двух `d` — ошибка компиляции.
- `~` сравнивает объекты по значению. Детали для примитивов, float NaN/epsilon, вложенных объектов и циклов ещё требуют определения. Не вводить неявную приблизительную точность самостоятельно.
- Логические операции: одиночные `&`, `|`, `!`, `^`. Это заменяет прежний согласованный набор словесных форм и двойных знаков; их сохранение как алиасов не утверждено.
- Побитовые операции — функции `ba`, `bo`, `bx`, `sh` (он же `shr`), `shl`, `ush`, `inv`.

Нужно определить короткое замыкание `&`/`|`, типы операндов побитовых функций, ширину и знак сдвига. Конфликт return со сравнением `>` устранён выбором `@`. Двойное назначение `|` для будущего pipe остаётся задачей будущей грамматики.

## Null на границе внешних библиотек

- Коллекции lac не содержат null.
- Для nullable-коллекций внешних библиотек обязательна `.fnn` (`filterNotNull`) или `.n` (`ifHaveNull`).
- Для внешней nullable-переменной обязателен `val ? A : B` с обработкой null.

Нужны отдельные внешние nullable-типы до нормализации, правила типов ветвей, поведение `.n`, а также различие null-проверки и bool-условия. Предложение: определить `? :` по статическому типу левого операнда: bool-ветвление либо проверка внешнего nullable. Доступ к полям до проверки компилятор отклоняет. Это детализация, не готовая сигнатура.

## Память: единственный владелец

- Стараемся обходиться без GC, иметь минимальный runtime и близость к C.
- Принят один владелец объекта, как в Rust. Автоматическое освобождение не требует ручного `delete` или явного вызова деструктора.
- Для владеющих значений присваивание передаёт владение; источник после передачи использовать нельзя. Это заменяет прежнее копирование адреса с созданием равноправной владеющей ссылки. Примитивы продолжают копироваться по значению.
- Заимствование предоставляет временный доступ без передачи владения и не должно переживать владельца. Точный синтаксис и объём статических проверок ещё не выбраны; полного копирования системы типов Rust это решение не требует.
- Компилятор генерирует освобождение при выходе владельца из scope, замене его значения и раннем возврате. Переданное или возвращённое владение в старом scope не освобождается. Счётчик ссылок не нужен.
- Перекрёстные ссылки разрешены, анализ их циклов не требуется; ответственность оставляется программисту. Предложен профайлер памяти.
- Ранее заявленная Java-подобная автоматическая сборка недостижимых циклов больше не является требованием.
- Уникальное владение выбрано основой; регионы и ARC из `memory-without-gc.md` остаются рассмотренными альтернативами, не частью принятого ядра.

Следует различать цикл адресных связей и цикл владеющих связей. Единственность владельца сама по себе не заменяет правила времени жизни и доступности владельца. Перекрёстные невладеющие связи требуют заимствований или идентификаторов. Нужно согласовать прежнее пожелание не проверять перекрёстные ссылки с безопасностью заимствований: непроверяемый адрес может стать висячим. Профайлер может обнаруживать проблемы в исследованных запусках, но не гарантирует безопасность всех программ.

До первого драфта нужно определить: перемещение элементов в коллекции; время жизни ленивых sequence; захваты лямбд; возврат владельца; семантику `.cp` и `.dpcp`. Поверхностная копия не может создать второго владельца вложенного heap-объекта: нужны отдельные правила копирования или заимствования. Для безопасных заимствований предлагается правило Rust: несколько читателей либо один исключительный изменяемый доступ; это детализация для дальнейшего утверждения.

«Без отдельного runtime lac» совместимо с C-кодом cleanup и системным allocator. «Без какого-либо кода освобождения/учёта при исполнении» несовместимо с автоматическим повторным использованием произвольно выделенной динамической памяти. Требуется выбрать точную границу.
