# Владение памятью lac без GC

Дата: 2026-10-01. Пользователь выбрал единственного владельца, как в Rust. Вариант 1 — принятое направление; варианты 2 и 3 сохранены для сравнения и не входят в утверждённое ядро. Точные правила заимствований и копирования ещё проектируются.

## Что можно убрать

Можно обойтись без виртуальной машины, tracing GC, отдельной runtime-библиотеки lac, ручного `delete` и пользовательского деструктора. Компилятор вставляет в генерируемый C необходимые `free`, освобождение полей и закрытие ресурсов. Они исполняются при выходе владельца, перезаписи и раннем `@val`; возвращаемое владение исключается из cleanup. Аллокатор C/ОС и исполняемые инструкции всё равно остаются.

Это scoped ownership/RAII: освобождение привязано к времени жизни владельца. [Rust: ownership](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html), [C++ Core Guidelines R.1, R.21](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-raii). Использование принципа не требует генерации C++ или принятия полного Rust.

## Вариант 1. Единственный владелец и перемещение

У heap-объекта ровно один владелец. Присваивание владельца передаёт владение, источник становится недоступным; примитивы копируются по значению. `.cp`/`.dpcp` предназначены для явного копирования, но их правила для вложенных владельцев нужно пересмотреть: поверхностная копия не может породить второго владельца того же объекта. Временный доступ функции — невладеющее заимствование, не переживающее владельца. Нужна хотя бы консервативная статическая проверка времени жизни для безопасного режима: [Rust: borrowing](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html).

Плюсы: нет RC-заголовка и увеличений счётчика; генерируется обычный cleanup C. Изменение ранее принятого присваивания как копирования общей ссылки теперь согласовано пользователем. Ссылочные коллекции должны различать владельца элемента и заимствованный доступ. Синтаксис заимствований ещё не выбран; несколько читателей либо один исключительный изменяемый доступ предлагаются как следующий шаг по модели Rust.

Перекрёстные связи можно представлять невладеющими ссылками или IDs. Одной проверки количества владельцев недостаточно: правила перемещения и времени жизни должны исключить потерю доступного владельца и висячие заимствования. Если проверки невладеющих связей намеренно отключены, безопасность их времени жизни остаётся обязанностью программиста; отсутствие GC не делает их автоматически безопасными.

## Вариант 2. Регион/арена для группы объектов

Все объекты задачи принадлежат одному региону. Адреса внутри него свободно копируются и могут образовывать циклы; регион освобождается целиком при выходе владельца. Для возврата графа передаётся владение регионом либо данные копируются в более долгоживущий регион.

Плюсы: близко к C, подходит небольшим batch-скриптам, не нужен обход цикла для освобождения региона. Минусы: отдельный объект удерживается до конца региона; ссылки наружу должны иметь ограниченное время жизни; ресурсы вроде файлов требуют отдельного cleanup. Сама arena может иметь небольшой исполняемый allocator/список блоков; назвать это полностью отсутствующим runtime было бы неточно. Альтернатива для очень ограниченных регионов — фиксированный заранее известный буфер, но он не заменяет произвольную динамическую память.

Это проектный вариант для lac, а не обещание измеренной производительности. Для произвольных межрегионных ссылок нужно объявить дисциплину времени жизни или принять ответственность программиста.

## Вариант 3. ARC без сборки циклов

Присваивание копирует ссылку и увеличивает счётчик; cleanup уменьшает его и освобождает при нуле. Генератор вставляет операции в C, без отдельной внешней runtime-библиотеки; заголовок объекта и проверки при исполнении остаются. По семантике это ближе всего к ранее выбранным общим ссылкам.

Плюсы: автоматическое освобождение большинства объектов и сохранение sharing. Минусы: это минимальный runtime учёта владения, а не нулевая runtime-стоимость. Владеющие циклы допускаются, но могут утекать; это совместимо с намеренно принятым ограничением, если оно явно отражено в документации. [Apple: ARC и циклы](https://developer.apple.com/videos/play/wwdc2021/10216/).

Невладеющие ссылки также требуют правил; автоматическое безопасное обнуление weak-ссылок потребует дополнительного учёта и внешнего nullable-типа.

## Рекомендуемый выбор зависит от приоритета

| Приоритет | Предложение |
| --- | --- |
| Минимальная стоимость учёта и предсказуемое освобождение отдельных объектов | Уникальное владение + перемещение + ограниченные заимствования |
| Небольшие задачи с графом произвольных ссылок | Регион/арена, освобождение целиком |
| Сохранение присваивания общей ссылки и минимум изменения языка | ARC, явно допускающий утечки циклов |

Уникальное владение принято основой. Явный регион для графов/обработки задания остаётся возможным будущим расширением. Независимые равноправные владельцы одного адреса не входят в текущую модель.

Не рекомендуется просто делать `free` по scope первого создателя при неконтролируемом копировании адресов: это создаёт use-after-free. Escape analysis может оптимизировать отдельные случаи, но не заменяет опубликованный контракт владения.

## Лямбды, коллекции, ошибки и C API

Замыкание владеет захваченными ресурсами либо заимствует их на допустимый срок. Возвращаемое замыкание не сохраняет локальные адреса. Ленивая трансформация массива обязана удерживать источник по выбранной модели; копирование iterator-ссылки и передача владельца — разные действия.

При мутации через `fe` замена элемента освобождает старого владельца только после безопасного получения нового. Ссылочные поля могут ссылаться на общий объект лишь если это допускает выбранная модель. Глубокая копия циклического графа по-прежнему требует таблицы соответствий либо явного отказа от таких объектов.

Для nullable-указателя C надо определить, освобождается ли он lac, C-функцией или вообще не принадлежит вызывающему коду. Проверка null не даёт права на `free`. На границе FFI нужны borrowed/owned контракты.

Ошибки и ранний `@` должны проходить через cleanup. Для первого генератора достаточно явных ветвей и единого пути возврата; полноценное unwinding пока не требуется. При аварийном прекращении процесса ОС может вернуть память, но нельзя обещать выполнение закрытия внешних ресурсов.

## Профилирование

Отладочный режим может учитывать allocation/free, отмечать место создания, показывать живые объекты по окончании задачи и динамически проверять отдельные ошибки адресов. Такой режим добавляет инструментацию, которую можно исключить из обычной сборки. Он не доказательство безопасности программы и не делает цикл с ненулевым RC автоматически освобождаемым.
